D · 权限与安全边界第 12 章

hooks、确认与拒绝后的继续

规则和模式给出了判定，工具调用还要完成一次授权交互。本章主要读 services/tools/toolExecution.ts:798-841、services/tools/toolHooks.ts:321-393、utils/permissions/permissions.ts:393-446 与 hooks/toolPermission/handlers/interactiveHandler.ts:83-101、hooks/toolPermission/handlers/interactiveHandler.ts:410-458。PreToolUse、PermissionRequest 和用户确认都可能改变结果，但它们发生在不同位置；理解顺序和单次结算，比把它们统称为“外部审批”更能解释实际执行。

工具执行前先接收 hook 结果

toolExecution 迭代 runPreToolUseHooks，接收进度消息、权限结果、updatedInput、阻止继续和停止原因。hook 只改输入而没给权限决定时，也会替换 processedInput 供普通权限流程使用。工具名不变，参数已经可能不同；后续匹配应针对更新后的对象（D-39）。

原文依据：services/tools/toolExecution.ts:798-841。

把输入修改和授权分开，是这段 switch 的实际结构。一个 hook 修正路径不等于批准新路径，提供上下文也不等于拒绝执行；结果类型决定下个动作。工具执行层随后调用 resolveHookPermissionDecision 接成最终决定。排查“用户看到的命令与执行命令不同”时，先查这一更新链，比仅搜对话中原始 input 更直接。

hook allow 仍要过规则

resolveHookPermissionDecision 取 hook 更新输入，检查 requiresUserInteraction 与 requireCanUseTool。交互工具如果 hook 提供了更新输入，可以把它视作已满足交互；否则仍进 canUseTool。普通 hook allow 调用规则子管线，deny 可以覆盖 allow，ask 仍需走询问。原文注释明确声明 hook allow 不绕过 settings deny/ask（D-39）。

原文依据：services/tools/toolHooks.ts:321-393。

这个复查函数与完整权限函数不一样：规则子管线不跑 auto 分类器、模式变换或 PermissionRequest hooks，用户交互要求由调用者预查（utils/permissions/permissions.ts:1060-1070）。前面在第 10 章读到的分层，在这里给出具体复用者。若把 hook 批准当任意模式的最终通行证，就会遗漏这次复查和交互守卫。

工具执行状态也要以更新后的 input 为准。hook 已变更对象，复查却若拿旧对象就解释错授权目标；当前代码返回 decision 与 input 两部分，说明判定结果和最终参数在这一接口中并行传递。它并没有让 message 文本替代参数验证，文件工具还有第 8 章的先读检查。

PermissionRequest 是询问阶段的事件

无头路径运行 executePermissionRequestHooks，让 hook 在自动拒绝前给决定。allow 可以提供 updatedInput；updatedPermissions 会持久化并应用到当前 AppState，然后返回带 hook 原因的 allow。一次调用批准与权限规则更新是两个字段，可以一起出现，也可以只批准当前输入（D-40）。

原文依据：utils/permissions/permissions.ts:393-446。

shouldAvoidPermissionPrompts 为真且没有 hook 决定，回退 deny，原因是当前环境没有提示能力。它不会因无人显示对话框就自动放行。auto 分类器检查又在此前，使它可在无头环境工作；不可分类器批准的安全检查另按第 11 章返回或拒绝（D-18、D-38）。

原文依据：utils/permissions/permissions.ts:929-952。

这条顺序解释了“无头”不是一项权限模式。它是交互能力约束，仍能运行 hook 或分类器，能否执行取决于先前判定。把无头直接等同 bypass 或 dontAsk，会把不同字段的行为混在一起：dontAsk 主动把 ask 转 deny，无头路径则先给请求 hook 处理机会。

确认队列与异步检查竞速

交互 handler 用 result.updatedInput 或原 input 显示请求，并先入确认队列。PermissionRequest hooks 异步执行，返回后必须 claim 成功才结算；随后取消 bridge 请求、退订 channel、移除队列项并 resolveOnce。Bash 分类器的继续条件同样看是否已结算和用户是否交互（D-41）。

原文依据：hooks/toolPermission/handlers/interactiveHandler.ts:83-101。

原文依据：hooks/toolPermission/handlers/interactiveHandler.ts:410-458。

这里“谁先得到结果”与“谁还允许提交结果”分别由异步返回和 claim/状态条件控制。不能仅说分类器较快就必然压过用户反馈；shouldContinue 检查 userInteracted，hook 路径也要拿到结算资格。源码展示取消其他来源和移除队列的动作，避免同一次请求被不同批准重复交付。

useCanUseTool 还有 coordinator、swarm worker 和 Bash 推测分类器路径，普通 ask 最后进入交互 handler；对应分支见 hooks/useCanUseTool.tsx:96-170。当前取证不复述渲染层，只追谁产生与消费权限结果。显示一个对话框是询问的载体，不能反过来证明其他路径不会返回结果。

取消与拒绝还要告诉模型

cancelAndAbort 选择普通或子 agent 的拒绝文本，可带用户反馈；显式 abort，或无反馈且无附加内容的非子 agent 取消，会中止回合。返回行为为 ask 并不意味着这里仍等待一个新批准，它是取消路径使用的判定结构。具体对象要按方法语义读（D-20）。

原文依据：hooks/toolPermission/PermissionContext.ts:154-173。

拒绝怎样回到模型，已在第 4 章连同公共指导完整引用（services/tools/toolExecution.ts:1023-1038、utils/permissions/permissions.ts:857-868）。从当前交互链继续查时，下一站就是那条回灌，而不是重新发起同一个确认队列项。各消息构造路径的范围限制也沿用该章说明。

第 4 章的“别原样重试，先理解原因”因此有实际接收位置：模型下一步会读到工具结果里的错误说明（constants/prompts.ts:186-197）。它不是执行器自动替用户修正任务，而是把事实与拒绝理由留给后续推理；作者要求合理替代而非恶意绕过的文本也只能在对应构造路径里出现。

提问工具不是任意批准的通道

AskUserQuestion 澄清需求、ExitPlanMode 展示并审批计划的区别已在第 9 章展开（tools/AskUserQuestionTool/prompt.ts:32-44、tools/ExitPlanModeTool/prompt.ts:6-29）。这里保留它与 requiresUserInteraction 的关联：某工具需要真正的用户交互，不能因为模式通常自动许可就省略；hook 更新输入满足交互的特殊路径也有具体条件。用户回答的内容和持久规则修改不能凭空互相转换。

登录后 bypass 的一次性检查标志会重置，远程跳过在启动 hook 的 effect 中；它不写在所有检查入口内部（utils/permissions/bypassPermissionsKillswitch.ts:49-73）。这也是交互外壳与判定函数要分层读取的例子：界面启动是否调用，和函数自身拿到上下文后如何处理，分别由不同代码说明。

本章的终点是一次调用已经有结果，其他等待来源也被取消或保留。批准后的环境仍可能拒绝文件访问或网络连接；输入验证和执行隔离不会因对话结算而消失。下一章继续读路径保护与沙箱转换，说明权限 allow 之后还有哪些具体边界。
