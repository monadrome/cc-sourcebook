E · 上下文与记忆预算第 15 章

压缩怎样删内容，又怎样让工作接着走

第 14 章区分预算口径，这章读 query.ts:365-426、query.ts:428-468 的缩减次序与 services/compact/compact.ts:330-338、services/compact/compact.ts:518-624、services/compact/compact.ts:723-747 的重建结果。问题不只是“摘要写得够不够”：宿主还须维持消息配对、工具发现和缓存状态。下面沿删除、回退与恢复追踪这些约束，检验哪些内容能省掉，哪些关系必须继续成立。

先改内容，不能只靠旧 usage 判断压力

query 在摘要前改消息，usage 却来自已经发生的 API 响应。二者不同步，所以删过结果后还需另传释放量；仅看末次 usage，会把被删除的材料继续算在压力里（E-03）。

原文依据：query.ts:365-426。

工具结果替换先于按 tool_use_id 操作的微压缩，注释给出组合理由：结果正文改变不影响后者找调用 ID。snip 同时保留 usage 所在尾部，所以把 tokensFreed 单独送后面。消息数组已缩短和估算基准已变小，不是同一个事实。

原文依据：query.ts:428-468。

collapse 在 autocompact 前，可让后者不再触发；注释还说明它只是读时投影，不往 REPL 数组塞同样的摘要。这里能核验的是调用关系，独立实现仍未展开。不能把几个 if 分支解释为每轮执行一串彼此累积的全量摘要。

微压缩删的是结果，不是整条协议关系

时间门槛要结合 enabled 读。六十分钟与保留五条只是开启后的参数，不能因进程空闲过久就推断它默认已清理（E-09）。

原文依据：services/compact/timeBasedMCConfig.ts:18-43。

默认 disabled 将整个时间路径挡住；后面的 cached 路径又有另一套特性与模型条件。配置里两个数值不会替代这些入口，microcompact 被调用也可以原样返回。

原文依据：services/compact/microCompact.ts:243-293。

时间路径成功会先短路，未发生才继续内部 cache-editing 判断。两种实现因此不是一个默认动作的两步；原样返回也不是压缩失败，它可能只是当前来源或模型不符合条件。下一步要看允许清除什么。

原文依据：services/compact/microCompact.ts:36-50。

这份集合把能力名称变成清理候选，不把所有工具结果一概视为同样可丢。原消息仍要能解释模型调用了谁，真正替换只发生在命中结果上，而不是把 assistant 的调用记录一起删掉。

原文依据：services/compact/microCompact.ts:422-496。

ID 留着、正文换占位，说明“工具已调用”和“工具结果还可见”的寿命分开。保留数至少一条，配置零值不会把最近结果全清掉；来源不明也不触发时间路径。后续工作若需旧正文，必须靠已转存信息或回查，不能把占位当原结果摘要。

API 微压缩是另一个控制入口：客户端设置 context-management，并不在此直接修改本地字符串。先看 thinking 的选择，再看工具清理，避免把二者合成一个总开关（E-11）。

原文依据：services/compact/apiMicrocompact.ts:14-32。

保留全部 thinking 是默认请求策略，clearAllThinking 又实际保留最后一个 turn，而非名字字面上的“全删”。这类参数须按输出配置解释，不能只凭函数名推断模型下一次完全没有 thinking。

原文依据：services/compact/apiMicrocompact.ts:63-153。

工具清理只在内部用户及环境条件满足时加入；thinking 的策略可以存在而工具策略不加入。trigger 与 keep 是请求目标，也不等于本地已释放对应 token 数。客户端清理、服务器清理和结果投影各有自己的记录，下一轮压力判断必须看哪条路径实际返回了结果。

触发许可与失败计数分别阻止重试

自动压缩的允许条件把用户关闭、子任务递归和实验策略放在占用阈值前；阈值不是一项无条件运行授权（E-07）。

笔记维护和 compact fork 不再自动压缩，避免生成摘要的子任务又触发自己的摘要。reactive-only 路径也可拒绝主动触发。这些 early return 表示选择另一策略或跳过，不应全部统计成模型压缩失败。

这里才把占用与释放量对齐，然后比较当前阈值。用户开关、来源条件和窗口压力需一起满足；“占用很高但没主动 compact”可以由前面的策略解释，不能只回算数字指责阈值没生效。

允许尝试之后，还有针对连续失败的独立断路器。注释记录极端失败次数及 API 浪费，实际限制靠跨轮保存的计数，不靠模型理解一段停止指导（E-08）。

三次是停止继续尝试的次数，不是最多三次一定获得摘要的承诺。必须看入口是否在阈值判断前检查旧计数，以及调用者是否把新的计数传回来。

已有失败达到上限会连 shouldAutoCompact 都跳过；仍未到阈值也直接返回。二者都可以没有 compactionResult，却代表不同原因。真正生成路径又先尝试笔记，只有不适用才转传统模型摘要。

笔记成功与传统摘要成功都清旧总结游标并做清理，但返回的字段不完全相同；传统异常才明确增加连续失败计数。不能把笔记路径的 null 直接当一次相同的 API 失败，它是让另一条路径继续的信号。

调用者把计数写回 tracking，下一轮才记得已经失败；成功后才用重建结果替换 messagesForQuery。没有生成摘要不意味着历史已被删除。模型说明、客户端返回值与实际替换数组的时点，要沿这两端接起来。

异常处理还有一个容易漏掉的例外：用户中止只跳过错误日志，后面的失败加一仍执行。这里的计数不能窄称为“连续 API 技术故障次数”。它按当前 catch 的返回值跨轮累积，是否记录错误与是否影响断路器是分开的选择（services/compact/autoCompact.ts:287-350）。

摘要的指令合并不代替运行状态保存

PreCompact 可影响摘要应保留什么，但它返回的指令不是原始对话事件。用户要求与 hook 补充按字符串顺序合并，不能因此声称宿主已逐条裁定两份指令的冲突（E-13）。

原文依据：services/compact/compact.ts:374-423。

auto/manual 与 customInstructions 随事件传入，用户文本在前、hook 文本在后。这个顺序能重现模型输入，却不决定摘要一定完整保存哪项要求；后面的构造调用才消费合并结果。

原文依据：services/compact/compact.ts:435-443。

摘要请求使用合并后的指令，所以“没有自定义摘要要求”只描述用户参数，不表示没有 hook 指令。禁止工具与输出结构见第 6 章（services/compact/prompt.ts:12-26、services/compact/prompt.ts:28-44、services/compact/prompt.ts:61-143、services/compact/prompt.ts:269-303），这里开始检查摘要写成后还缺哪些宿主状态。

摘要之外还要重建可执行的会话

buildPostCompactMessages 把边界、摘要、保留消息和附件分别接回；这里的顺序决定新对话先看到什么，并没有把所有类型压成一个摘要字符串（E-16）。

保留原文和重建附件是摘要外的输入来源，因此摘要字数不能代表整个压缩后占用。真正恢复过程还需重新宣布工具、计划与指令，不能只保留“我已经做过什么”的叙述。

原文依据：services/compact/compact.ts:518-624。

发现工具名被写进 compactMetadata，因为摘要不会保留 tool_reference 协议块；名字出现在自然语言里也无法替 schema 过滤提供这个集合。读文件缓存会清、恢复文件却重新读取，说明已知状态和可编辑视图也要重新建立。

原文依据：services/compact/compact.ts:723-747。

PostCompact 得到摘要并可返回显示消息，但它不替前面的数组装配生成所有附件。这种完成事件与输入恢复分开，能解释为什么压缩结束通知、用户看到的说明和下次 API 的材料不是同一份结果。

恢复预算针对不同集合，不能简单相乘相加

文件数、单项目标和附件总粗估同时存在；技能另有自己的额度。五份文件乘五千不意味着五万总帽写错，因为单文件读取目标与序列化附件估算的对象不同（E-15）。

原文依据：services/compact/compact.ts:122-131。

常量只给候选上限，选哪些文件还要看最近读取及保留消息是否已经包含它们。已在保留尾部出现的路径不该再花恢复额度，这个判断把恢复管线接回消息选择。

原文依据：services/compact/compact.ts:1415-1464。

文件先筛选和读取，再对完整附件的 JSON 粗估累加。这个总帽处理的是构造结果，并不能反推每份原始文件都完整回来了；读取失败或预算不足都可能让某候选缺席。恢复是有选择的补偿，不是历史所有读取的重放。

超额候选只在 filter 中返回 false，没有中止后续候选检查。因此，最近文件优先并不等于只能保留排序后的一段连续前缀；后面更小的附件仍可能放得下。文件时序决定尝试顺序，大小预算决定保留集合，两种条件在这里共同起效。

原文依据：services/compact/compact.ts:1494-1534。

技能正文先按单项目标截，再受独立总额限制；近期技能可保留但其尾部可能不在上下文中。索引发现预算又是第14章另一套对象。转录回查路径保留了进一步找材料的办法（services/compact/prompt.ts:305-374），并没有让被裁部分自动进入新消息。

保留目标要让位于 API 配对

笔记压缩的 maxTokens 注释称 hard cap，实际算法却在常规取舍后修复消息关系。先保留配置原句，才能看到后面究竟在哪一步扩大范围（E-17）。

原文依据：services/compact/sessionMemoryCompact.ts:44-61。

最低 token、最低文本消息数和最高目标不是互相可替代的指标；它们限制不同形态的保留。远端配置只校验各项正数，还没有在这个片段里保证最小与最大关系一致。

原文依据：services/compact/sessionMemoryCompact.ts:98-130。

单项有效不代表组合已能同时满足所有愿望。启用选择也独立于大小配置，尤其启用环境变量先于禁用变量；它们同时为真时，当前函数先返回 true，不能概括成“禁用变量总优先”。

原文依据：services/compact/sessionMemoryCompact.ts:403-432。

默认要求两个 gate，但环境启用可绕过这条默认组合；这只允许尝试笔记路径，仍不保证有可用笔记。消息保留的实际范围接下来由已有边界、目标条件与协议修复共同产生。

原文依据：services/compact/sessionMemoryCompact.ts:232-314。

保留区里的 tool_result 会把切点向前拉到缺失 tool_use，同 message.id 的更早分片又可继续扩大。协议完整性因此不是“压到四万后再删除多余一点”，而是允许保留超出普通目标的关系材料。

原文依据：services/compact/sessionMemoryCompact.ts:316-397。

普通循环先按总结位置、token 和文本条数选切点，最后才调用前面的修复。hard cap 的张力来自这个真实次序，不应替实现删除修复步骤或替注释改口。构造完仍过大时，还有整条笔记方案的回退检查。

原文依据：services/compact/sessionMemoryCompact.ts:514-630。

空笔记、无效总结游标或结果达自动阈值返回 null，交回传统路径；它不会为坚持笔记模式强行截坏配对。恢复会话缺游标又有末条计算的例外，须与“游标存在但已失效”区分。第16章维护游标的安全条件由此有了消费者。

提醒总量与硬裁每节不是同一保证

两项笔记常量分别支撑总量提醒与节大小判断，并不表明插入前有一个对应的全文件硬裁器（E-23）。

这些数字先用于向模型要求压缩内容。若模型未遵守，宿主还有下一道措施，但它的检查对象与提醒里的总量未必相同。

提醒要求优先保存 Current State 和 Errors & Corrections，属于语义取舍。硬裁函数却不比较哪句话重要，只沿标题切节和按字符、行边界保留；两者不能被概括为同一种智能压缩。

flushSessionSection 没有标题就原样返回，按节裁切也没有实现一万二的整文件硬帽；有标题的过长节则保开头并加标记。这是总量提醒与实际裁切边界的具体差别，最终结果能否用作压缩仍由前面的大小回退判断兜住。

更具体地说，语义优先级不会改变硬裁的保留方向。即使某节末尾有重要纠正，当前循环也只是累计开头的行，超限即停。提醒要求模型提前整理与最终裁切为何都存在，由此有了实际关系：前者能改变内容安排，后者只能限制已有排列（services/SessionMemory/prompts.ts:249-324）。

重装还要清外层用户上下文缓存，具体生命周期见第 2 章（services/compact/postCompactCleanup.ts:12-64、commands/clear/caches.ts:47-84、commands/clear/conversation.ts:124-130、utils/claudemd.ts:1042-1086、utils/claudemd.ts:1088-1130）。恢复附件、清快照和保存游标各维护不同关系。压缩到此仍是当前会话的继续；下一章将这套有限材料的保存职责与跨会话记忆分开。
