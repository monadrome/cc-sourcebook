C · 工具提示词第 07 章

工具接口、描述与发现协议

工具卷配对读模型描述与实际分支，方法边界见阅读说明。本章从 Tool.ts:386-406、Tool.ts:518-524 和 utils/api.ts:136-178、utils/api.ts:208-230、tools/BashTool/BashTool.tsx:426-433 追文本怎样进入API。两个description名字相同却有不同消费者，能力进入工具池、被模型发现、这次获准执行也分属不同阶段；这些区别比一份工具名清单更能解释调用行为。

一次调用的说明不能代替模型协议

Tool把具体input的说明、schema与执行性质放在同一个接口，但没有让说明文字自动实现只读、并发或破坏性判断。先读方法签名，才能知道哪个字段消费输入，哪个字段只陈述用途（C-01）。

原文依据：Tool.ts:386-406。

description拿到本次参数，而isReadOnly等方法另行返回性质；文本中写“只读”不能替这些方法生成返回值。破坏性注释还有默认与适用情境，读者不能只根据工具名字决定运行时属性。prompt则面向另一组上下文。

prompt接工具和agent集合，不接本次input，说明它可以描述当前可用能力，而不是展示刚刚生成的命令。调用者允许哪些agent类型也能进入这份文字。接下来同名API字段的赋值，才将这两个方法真正区分开。

原文依据：utils/api.ts:136-178。

API description来自prompt，缓存键却主要是工具名及可选JSON schema，不包含这次description闭包的一切状态。注释说基础schema要稳定，故不能因工具列表或gate变动就假定描述同步重算。改变输入schema内容与改变每请求延迟标记，又走不同处理。

原文依据：utils/api.ts:208-230。

defer_loading与cache_control叠在复制的基础对象上，不回写缓存。一个工具本轮被延迟，与它的长描述重新生成，是两件事。生命周期已在第2章详述；这里用Bash对拍文案实际从哪个方法来。

Bash的description只是输入说明或Run shell command，prompt才返回包含操作规则的getSimplePrompt。停在前者会误以为工具只给一行能力介绍；停在API字段又不回溯赋值，则会把面向模型的协议错当成这次命令的摘要。

这两个方法的差异还影响缓存审计：API缓存的是prompt生成的描述，工具执行却仍以具体input调用description。一个变更只改了调用摘要，未必会让模型看到的新规则更新；一个变更只改了prompt，也未必改变用户看到的单次命令说明。检查工具行为时，先标出文字的消费者，再看哪一个对象参与schema缓存。

注册、可见与许可逐层收窄

注册表能列出某个对象，不代表当前会话一定把它送给模型。构建和运行条件先影响基础候选，再由权限与可用性筛选决定实际视野（C-03）。

原文依据：tools.ts:193-230。

嵌入式搜索时不注册独立搜索工具，另有按用户与模式加入的对象。因此，模板里要求某工具之前，还得有对应工具集合；不能拿完整注册表当每次请求的实际能力。

原文依据：tools.ts:253-298。

整工具deny会提前移除名称，简单模式还有独立的基础集合；这使“工具不存在”既可能是能力选择，也可能是禁用。内容级规则却不能在此完整判定，它还没有本次输入。检查一次调用是否允许，应继续走第10章的执行权限，而不凭当前工具可见作结论。

原文依据：tools.ts:300-326。

普通路径再检查isEnabled并剔除特殊或REPL包装原语。前一块决定选哪组工具，这一块决定组内哪些能直接用；coordinator与普通会话不应共享一个无条件清单。MCP接入后还要解决同名候选。

这三步的结果是“模型视野”，不是“权限结论”。工具可以因模式不适合而不出现，也可以出现后因为参数命中 deny 而被拒绝；反过来，一个出现在列表里的工具也可能只在当前特性开关打开时存在。把列表快照和调用判定放在同一张表里，会丢掉这些时间点差异。

原文依据：tools.ts:329-366。

内置与MCP各自排序、连接后去重，使当前函数中的内置候选占先；注释把分区稳定性关联缓存。这个结果只说明该组装入口的冲突处理，不证明SDK所有替代路径都相同。旧规则名归一也独立于工具池，展示名与权限名不能随意互换（utils/permissions/permissionRuleParser.ts:21-33）。

名称发现解决不了参数未知

ToolSearch用完整schema的获得状态定义可调用，而不是用“模型听过名字”定义能力。提示在两种公告位置之间选择，同时把准确名称查询与关键词匹配分开（C-18）。

原文依据：tools/ToolSearchTool/prompt.ts:27-51。

位置提示的gate必须与真正公告工具的机制对齐，注释特意说明同一个判断为何在此复制。否则文案会让模型去错误位置找名字。返回schema的编码又与顶层工具定义一致，承担从发现到调用的协议转换。

这份prompt由固定头尾与运行时位置提示拼成；不是每次把工具全集直接列入描述。判断它提供了什么，应区分指向清单的文字与清单本身。API是否实际延迟工具，还由下面的谓词与请求开关控制。

原文依据：tools/ToolSearchTool/prompt.ts:53-117。

alwaysLoad先于isMcp，通信工具与Agent也有立即可见例外，所以注释里的“所有MCP延迟”须带前置豁免。searchHint还可存在于对象，但formatDeferredToolLine只给名字；注释记录其A/B无收益，不等于字段从系统中消失。保存、展示与试验结论分别有来源。

isDeferredTool的判断不直接写API字段，willDefer还要useToolSearch为真。把内部“可以延迟”的性质翻成“本轮一定延迟”，就跳过了这个请求条件。下一块才消费结果构造schema。

原文依据：services/api/claude.ts:1231-1246。

实际发送映射filteredTools，却给prompt传完整tools，注释说明描述可以知道比实际发送集合更多的工具。模型在文字中见到名字，不表示完整schema已在同次请求出现。这正解释了为何发现入口、能力描述和调用许可需要分开核对。

这里有一个实际的先后关系：prompt可以告诉模型“有哪些东西能搜索”，API却只把当前筛选后的工具对象发送出去；ToolSearch返回schema后，模型才获得调用所需的参数形状。模型看到的候选、请求里已加载的对象和权限上下文里的工具集合因此可能处于三个阶段，不能用任一阶段替代另外两个。

技能清单的字符预算见第14章（tools/SkillTool/prompt.ts:20-50、tools/SkillTool/prompt.ts:68-171）。它控制发现描述，不直接缩减Skill调用的正文，也不替ToolSearch决定哪些schema被加载；同叫“少放一点文字”，控制对象不同。

空占位不表示外部工具没有协议

MCP本地prompt为空，不能据此评价真实工具给模型什么指导。空字段只是共同对象的起点，客户端会以服务器描述覆盖（C-33）。

这三行指向的是加载流程，尚未展示真正文字和元数据来源。要解释运行时能力，必须跟到tools/list响应；只对这个空文件统计提示词长度，会把MCP整类工具误算为无描述。

原文依据：services/mcp/client.ts:1743-1813。

同一外来description供调用说明使用，模型prompt却可能裁切；两者不必逐字等长。annotations又被客户端方法采用，性质来自服务端元数据，而不是模型读完描述推断。skip-prefix还会改变调用名，权限检查用mcpInfo保来源；不能用一个短名字串判断内置与外来对象等价。

这也解释了为什么本地MCPTool的空文件不是“工具没有提示词”的证据：真正的文字和schema在客户端把外部响应投影成Tool对象时才出现。外部description可以被截断，外部schema却直接进入inputJSONSchema；模型可读的说明与宿主可解析的参数甚至不共享同一截断策略。

净化Unicode与折叠searchHint换行解决表示问题，不能解释成已经验证描述可信。这里展示的是客户端怎样接纳和呈现外来字段，内容授权仍需沿权限链查。元数据可用于调度，未因此变成独立核验过的只读或安全证明。

资源发现保留服务器坐标

资源协议比工具搜索短，却同样防止把发现结果当成无来源的URI。列表附server字段，为后续读取提供必要坐标（C-32）。

原文依据：tools/ListMcpResourcesTool/prompt.ts:1-20。

省略server表示跨服务器枚举，不表示读任意资源时也能省来源。列表的输出补充与下一工具的必填参数形成一条传递关系；短描述的价值正在这个接口上。

原文依据：tools/ReadMcpResourceTool/prompt.ts:1-16。

读取要求server与uri，选定对象仍回到具体服务端。工具的流程复杂度可以不同：这里主要固定对象身份，Bash另安排操作步骤。不能因为文字短，就称它没有控制调用方式。

动态目录与坐标也进入调用约定

Config从设置注册表生成文案，让可选值和说明同源；但一个选项注册了，仍可在运行时被隐藏。模型目录不是静态枚举的原样复制（C-36）。

原文依据：tools/ConfigTool/prompt.ts:9-93。

voice项受kill-switch隐藏，model独立生成且可回退；实际写入规则不因这些文案存在而被自动实现。Get/Set又按value是否传入区分，取值真假不是选择操作的同义条件。RemoteTrigger的认证隔离理由同样归属为描述宣称，未展开的执行代码不能由文案补证（tools/RemoteTriggerTool/prompt.ts:1-15）。

Config的例子说明“动态描述”有两个方向：选项清单随着运行时状态变化，调用形状又由是否存在value决定。若只保存一次生成后的全文，模型可能看到过期选项；若只看schema，又看不到某项为什么可用。这里的微型harness同时承担发现当前选项和提示读写动作，执行器仍要检查真正的设置更新路径。

NotebookEdit的对象单位是cell，LSP则以文件位置识别目标。这两个短提示给出不同坐标原点，跨工具复制数字会改变所指对象（C-40）。

cell_number从零开始，insert/delete又改变单元格操作含义；它不是普通行号。下一份描述虽然也用位置参数，却不能继承这个起点。

原文依据：tools/LSPTool/prompt.ts:1-21。

LSP行与字符偏移从一开始，查询还需有服务端；相同数字不一定指同一文本位置。接口、发现、元数据和坐标到此各有落点。下一章继续检验操作前置条件，看“先读再写”的文案与输入验证在哪些分支相合、在哪些分支有例外。

从这里回看工具契约，参数单位是最小但最关键的边界。它不需要长篇流程就能改变一次调用的对象：cell_number从零开始，LSP位置从一开始，MCP资源还需server坐标。工具描述的价值不在于把所有规则写长，而在于把模型下一次输入必须带的坐标、名称和阶段说准确。
