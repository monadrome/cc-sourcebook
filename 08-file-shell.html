C · 工具提示词第 08 章

文件与 shell 工具怎样约束调用

这章沿 tools/FileReadTool/prompt.ts:4-21、tools/FileReadTool/prompt.ts:23-49、tools/FileEditTool/prompt.ts:1-28、tools/FileEditTool/FileEditTool.ts:223-264、tools/FileEditTool/FileEditTool.ts:275-343 与 tools/FileWriteTool/prompt.ts:1-18、tools/FileWriteTool/FileWriteTool.ts:179-221 读文件调用协议，再转向 Bash、PowerShell 和网页工具。值得看的不是“它能读写文件”这句能力介绍，而是缩进、读取状态、修改时间、字符串唯一性和 shell edition 这些具体条件。它们决定模型该如何构造下一次调用，也决定哪些前置要求已有实际分支支持。

Read 给编辑提供什么材料

Read的能力说明不能替代读权限，参数协议也不是所有格式共用一份正文视图。先看生成器怎样按文件形态组织输入，才能判断后面的编辑器拿到了哪种读取材料（C-09）。

原文依据：tools/FileReadTool/prompt.ts:4-21。

绝对路径和能力描述解决的是“模型怎样提出读取”，不是“读取是否获准”。同一段又接受不存在文件和目录转介，说明它在引导调用格式；路径安全、读权限和结果大小则在工具实现中另判。把一条能力文案直接当作读权限，会把两个消费者混在一起。

剩下的参数说明继续把输出格式拆开：行号、图片、PDF和目录各有接收方式。它们不是同一份“读取说明”的重复翻译，而是模型提交input时需要选择的不同形状。

原文依据：tools/FileReadTool/prompt.ts:23-49。

相同Read工具名可以提示不同读取策略，差别来自调用方配置而非模型临时偏好。大小提示、定位建议和行号格式分别进入模板，不能把某次生成的文案当成工具的永久规则（C-10）。

原文依据：tools/FileReadTool/FileReadTool.ts:339-378。

参数条件还改变了模型下一步能否定位修改目标：整文件阅读与已知区间阅读分别适合首次探索和回到既定位置。模板没有替模型决定哪种情境成立，而是把状态交给调用方；因此“Read总是带大小提示”或“总是要求offset”都比源码更强。

验证代码把这些参数转成实际读取上限；提示里的PDF页数只在相应feature打开时出现。文案是输入选择器，执行器仍需解释offset、limit和当前文件类型的组合。

从读取到替换有一次表示转换：给人定位的行号前缀不能作为要匹配的磁盘内容。Edit文案把这点与唯一性放在一起，让模型先选对正文片段，再决定替换一个还是全部匹配（C-11）。

原文依据：tools/FileEditTool/prompt.ts:1-28。

这份描述要求先读，但还没有展示检查发生在哪个分支。特别是old_string为空时，工具可能把请求解释为创建，不能只按“Edit”这个名字把所有调用都当已有文件替换。下一节用返回位置检验这条文字要求的实际范围。

先读要求的真实分支

Edit 检查到文件不存在且 old_string 为空时接受创建；已有文件为空、old_string 为空也直接接受。只有普通替换继续查 readFileState。于是，工具文案里的先读要求并不是“任何使用 Edit 都必须此前 Read 同一文件”；新建和空内容路径有实际早返回（C-11）。

原文依据：tools/FileEditTool/FileEditTool.ts:223-264。

普通编辑拒绝未读或 isPartialView，检查读后修改时间；Windows 时间戳变化但内容未变时，完整读取可用内容相同作回退。它用 findActualString 处理引号归一，再计算出现次数，replace_all 为假且多次匹配就返回错误。文本里的 exact replacement 因此不能解释成实现只接受字节完全相同的输入串。

原文依据：tools/FileEditTool/FileEditTool.ts:275-343。

时间戳检查和字符串检查是连续两道门。前者保护读到的文件没有在操作间变化，后者保护替换对象唯一；即便内容仍存在，读状态失效也会先拒绝。两个错误都返回 ask 形态，却表达不同的修复动作，不能都写成“再试一次”。

这条检查与第 3 章的指令处理链相接；原始/处理后内容如何分存已在那里说明。当前章只看消费方：readFileState.isPartialView 为真时，Edit 将它当作未满足读取要求，返回明确错误。读取者有材料与编辑器接受这份材料之间有具体布尔条件。

Write的覆盖风险首先是操作选择问题，随后才是读取状态问题。它要求模型在局部修改时选Edit，但执行验证不会仅凭“整文件重写”的意图就跳过已有内容保护（C-12）。

原文依据：tools/FileWriteTool/prompt.ts:1-18。

UNC早返回反而强化了分层：Write避免在权限检查前触发网络凭据行为，未存在文件则把创建交给后续流程；普通本地文件才需核对 mtime 和 partial view。这个例外保护的是检查过程本身，不是让UNC路径跳过用户授权。

已有文件的完整读取状态与新文件的不存在状态被验证器刻意分开；“Write会覆盖”只是文案告诉模型的风险，是否能够写仍由权限链决定。

原文依据：tools/FileWriteTool/FileWriteTool.ts:179-221。

Edit 与 Write 的差别不能只按“替换一些行”或“写整文件”来记。它们的新建例外、完整视图检查以及时间戳回退也不完全相同；短引与完整区间指针一起列出这些条件，调用出错时就能指出是哪一步拒绝，而不是一概怪工具不允许写。路径本身的敏感性详见第 13 章，当前章先把输入验证读完。

搜索工具会规定何时转交探索

搜索协议还限制谁承担多轮状态：直接查询适合一个范围明确的问题，开放调查则可能需要Agent接手。先看Grep的参数与转介，随后与Glob对照，才能分清共享策略和不同输入单位（C-13）。

原文依据：tools/GrepTool/prompt.ts:6-18。

Grep/Glob的“转交Agent”不是失败回退，而是对搜索范围的预判。单次工具已经能完成局部查询时继续派Agent只会增加一层交接；反过来，多轮探索若硬塞进一个regex调用，又会让模型自己维护状态。提示词在参数说明之外给了任务粒度的选择。

两个工具的参数虽不同，转交条件相同；这说明共享的是任务粒度判断，不是输出格式。文件名搜索和内容搜索仍应分别按工具schema构造。

原文依据：tools/GlobTool/prompt.ts:1-7。

系统段的定向搜索与广泛探索指导见第 4 章（constants/prompts.ts:371-381）；这里不用再抄一遍。两处文字可以配对检查：查明确文件或符号用直接工具，多轮开放调查才派 agent。描述并没有给开放探索一个自动分类器，调用者仍要按当前问题选择粒度。

Shell 的协议覆盖依赖和失败

Bash 的专用工具偏好与沙箱例外已在第 4 章详述（tools/BashTool/prompt.ts:275-295、tools/BashTool/prompt.ts:354-369、tools/BashTool/prompt.ts:163-190、tools/BashTool/prompt.ts:228-272）。命令编排部分另要求独立命令并行，有依赖用 &&，不在意前项失败时才用分号，不能用换行分开命令。等待规则要求后台通知、避免轮询、失败后诊断；Monitor 特性有另一份 sleep 指导（C-06）。

这组规则把 shell 操作符当成控制流标记：&&表达前项成功是后项前提，分号只表达顺序而不表达成功依赖；并行调用则把独立性留在消息级。等待规则又把完成通知与主动轮询分开，因而“命令能运行”不等于“等待方式符合协议”。

命令等待还有特性开关的分支，Monitor存在时提示更具体；无此工具时又给普通检查建议。相同的后台任务不会在两个构建中收到相同的等待协议。

这些操作符要求把失败语义也写进调用。若第二条只能在第一条成功后做，分号会表达错依赖；若两个命令只读取独立状态，合成一串又改变并行安排。源码用命令形式表达这组关系，但这一段不解析模型任务的真实依赖，不能因为 shell 字符合法就说工作流顺序已核验。

Git任务的规则可由内联文案承载，也可转给技能；文本长短不能独自证明安全纪律有没有。按用户类型选择的入口先决定规则从哪里来，再决定模型该怎样提交和核验（C-07）。

外部Git段把授权、暂存和提交后的核验排成流水线，内部用户短段则把同一套纪律转交给技能。两个版本不是一个流程删掉几行，而是把安全协议的承载位置改变了：审计时必须先确定用户类型和技能是否实际可用。

流程的前半段先得到状态与差异，后半段才写提交；它把“有改动”与“可以提交”分开。第一段的授权和安全操作是后续步骤的门，不是提交完成后的说明。

这段把暂存、消息和PR正文的约束接在同一个Git任务里，要求模型看完整分叉提交而非只读最后一次。它补的是审阅范围，和前一段的本地状态检查不是重复。

钩子失败后不能随手 amend，原句给出具体后果：失败意味着本次提交没发生，amend 会改到上一个提交。这个解释可直接引用，无须泛讲“谨慎有益”。暂存具体路径也是协议的一环，避免一条全量暂存命令包含无关文件；第 4 章授权范围与这里的 Git 操作步骤是相连的两个角度。

PowerShell把环境检测结果变成语法许可，未知edition时还选择保守的兼容文本。命令的正确形状不只取决于用户任务，还取决于宿主检测到了哪一条分支（C-34）。

原文依据：tools/PowerShellTool/prompt.ts:46-82。

edition分支对同一字符串给出不同合法语法，说明环境发现是生成命令的前置输入；它也会改变stderr和编码的解释。仅从PowerShell工具名或用户操作系统不能推出该分支，prompt生成器必须先检测edition，再拼调用协议。

运行段又把交互命令排除，给出here-string与独立/依赖命令的具体写法；语法兼容与调用编排是两个连续但不同的条件。

原文依据：tools/PowerShellTool/prompt.ts:105-145。

这组描述让环境信息落到实际语法选择。模型知道当前是 Windows，并不足以决定 PowerShell 可以用 &&；要读取 edition 分支。遇到命令失败时，环境不匹配、参数错、权限和沙箱原因各有证据来源，不能只因错误发生在 shell 就把它归为一种失败。

网页工具还会再次提示模型

WebFetch 给主模型说明 URL、提取 prompt、Markdown 转换、小模型处理、缓存和重定向；makeSecondaryModelPrompt 又给处理网页的模型拼接网页正文、调用者问题和 guidelines。预批准域名只要求简洁与相关细节，其他域名另有引用长度和原句使用要求。一个工具调用后面存在第二次文本装配（C-30）。

原文依据：tools/WebFetchTool/prompt.ts:1-46。

二级模型的输入边界也不同：网页正文放在分隔线内，调用者prompt随后出现，guidelines最后追加。非预批准域名的引用规则只约束二级模型的输出文字，不替主模型判断网页内容可信；来源边界仍由第4章的提示注入规则处理。

文案所称只读是工具用途描述，返回值所称摘要是处理结果形式；这两者都不让网页正文获得用户授权。第 4 章的提示注入提醒仍要求模型辨别外来结果。在这里继续查内容进入哪个提示位置，能看到问题和网页正文怎样并排，但没有给出“外来正文已经可信”的判定。

WebSearch 则读当前年月，要求查近期信息使用当前年份，最终答复附 Sources 并列相关 URL。这个要求跨过工具调用本身，伸到用户回复；地区可用性说明也只是当前描述中的文字，不能用它断言本机服务状态（C-31）。

原文依据：tools/WebSearchTool/prompt.ts:1-34。

WebSearch把检索日期约束延伸到最终答复的 Sources 区块，工具调用与用户可见的引用格式因此相连。日期来自运行时函数，来源URL来自搜索结果；当前提示词没有证明地区可用性或链接内容已验证，输出规范和数据真实性仍是两条链。

文件、shell、网页三组工具展示了不同层的微型流程：输入如何准备、失败后怎样重新调用、结果怎样写入最终答复。边界不止停在 schema。下一章继续看 Agent、计划和共享任务表，它们把这些动作组织成跨参与者的工作流。
