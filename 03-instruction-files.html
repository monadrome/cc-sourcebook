A · 系统提示词装配第 03 章

CLAUDE.md 的发现、导入与按路径加载

指令文件不是读一个当前目录里的 CLAUDE.md 就结束。主入口 utils/claudemd.ts:790-847 先装托管与用户材料，再遍历祖先目录；utils/attachments.ts:1777-1862 还在目标文件被访问后加载条件规则。本章沿这两条路径看文件如何进入上下文。它们值得连着读：漏掉延迟加载，就会误认为初始提示词已经包含项目的全部约束。

覆盖声明是一段包装文字

getClaudeMds 为每个条目加来源路径与用途说明，trim 内容后按输入顺序连接；没有条目则返回空串。前导 MEMORY_INSTRUCTION_PROMPT 要求遵循下面的指令，并声称覆盖任何默认行为。它是模型收到的要求，没有在这个函数里逐句解析用户规则，再算出“默认句子被哪一条替换”（A-23）。

原文依据：utils/claudemd.ts:1153-1195。

包装保留了来源差别：Project 是签入项目的说明，Local 是私人项目说明，User 是跨项目私人说明，AutoMem 和 TeamMem 则属记忆材料；团队文本还单独包 XML。都进入同一个 memory 文件集合，不等于用途相同。持久记忆的类型与检索留到第 16 章，这里关注人工指令文件的加载。

在进入这个包装前，getUserContext 还检查硬关闭与 bare。硬关闭变量始终关 CLAUDE.md；bare 模式仅在没有显式额外目录时关闭发现。它再调用 filterInjectedMemoryFiles，最后缓存生成的文本给分类器。文件存在、被发现和实际注入因此不是等价状态（context.ts:152-189）；实验过滤也可能让发现结果不进入当前上下文。

先读来源，再走目录

getMemoryFiles 起始准备 result 和 processedPaths，并从项目配置取得外部导入是否批准。Managed 文件总是先处理，随后的托管 rules 只取无条件项。User 则要 userSettings 来源启用；但一旦进入 User 路径，外部导入参数固定为 true。不同来源的导入范围就在调用参数上区分（A-24）。

（原文见 utils/config.ts:1779-1807，共 29 行，略）

原文依据：utils/config.ts:1779-1807。

这条参数差异不能简写成“所有指令文件都可以导入项目外文件”。Managed、Project、Local 使用 includeExternal 的审批结果，User 的两次调用明确允许外部导入。读取来源设置与导入文件位置也不是同一个检查：来源可以已启用，却仍在递归处理时跳过外部路径。后面看到 processMemoryFile 才能把两者接起来。

项目和本地文件从 originalCwd 向上收集目录，循环不包含文件系统根目录自身，然后 reverse 从祖先走回 CWD。每一层先处理 Project 的 CLAUDE.md、.claude/CLAUDE.md、无条件 rules，再处理 Local。它没有先读完所有目录的项目文件，最后才统一读本地文件；相邻两个目录的顺序需要按循环理解（A-25、A-26）。

文件头注释把后加载称为更高优先级，还说模型更注意后文；这是注释的行为主张。数组操作能确认加载顺序，不能独立复算模型对位置的注意程度。尤其是相邻目录混着 Project 与 Local 时，只背“managed、user、project、local”四级名称，会漏掉实际逐目录交错的顺序（utils/claudemd.ts:1-26）。

嵌套 worktree 另有 skipProject。向上走会经过 worktree 和主仓库，两份签入文件可能重复，所以代码检测 canonical root 与实际 git root，跳过主仓库范围内但不在 worktree 中的项目文件。本地文件不受 skipProject 控制；注释说它被 gitignore，可能只在主仓库存在。这是避免重复加载的特殊路径，不是关闭祖先遍历。

额外目录还要环境变量 CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD。该分支读取目录内两种 CLAUDE.md 和无条件 rules，但没有再查 projectSettings 来源开关。旁注释用显式 add-dir 以及 SDK 默认 settingSources 解释这个选择。bare 对显式输入的保留与这里的门控须同时核对，不能只看一个开关猜结果（A-27）。

文本先处理，导入再递归

读取文件后会去 frontmatter，借 Markdown lexer 去掉正文块注释并提取导入路径。代码块和行内代码里的注释保留，未闭合注释也保留；允许的文本扩展名之外的导入被拒。若上下文内容与磁盘不同，保存 rawContent 和 contentDiffersFromDisk，供后续读取状态使用（A-29）。

原文依据：utils/claudemd.ts:281-301。

作者推断这条双版本记录不宜只当作文档元数据。模型得到的是清理后的指令，文件工具后来编辑却要对磁盘原文匹配。若把整理后的内容冒充完整磁盘读取，old_string 可能对应不存在的片段，或丢失被过滤的部分。这个风险判断由附件逻辑选择 rawContent 并标部分视图的做法支持（utils/attachments.ts:1709-1775）。

导入解析只在文本节点找行首或空白后的 @ 路径，去片段标识、解转义空格，再按包含文件所在目录解析相对路径并去重。code 与 codespan 被跳过，列表和子 token 则递归。一个示例代码中的 @ 字符不应因表面格式相同就触发文件读取；文本节点边界是解析约束的一部分（A-30）。

原文依据：utils/claudemd.ts:448-535。

processMemoryFile 在路径已处理或 depth 达到 5 时返回空数组；符号链接目标也加入 processedPaths。它先 push 主文件，再处理导入并 append 子条目；外部路径且未批准时跳过。函数前注释却写 includes first，文件头也说导入在包含文件之前。必须把这两种说法并列，正文按数组操作说明当前实现（A-31）。

原文依据：utils/claudemd.ts:614-685。

这个差异直接影响我们画加载顺序，不能留成不痛不痒的“注释可能过时”。当前代码是父在前、子在后，下一层递归仍用同一规则；processedPaths 又让重复或环路停止。至于原作者曾想让哪个文件获得更高文本优先级，需要历史证据才能回答。本树里的冲突不足以替作者解释原因，故到数组操作为止。

claudeMdExcludes 也限定来源。Managed、AutoMem、TeamMem 直接不排除，User、Project、Local 才查配置；Windows 分隔符会规范化，绝对模式另扩真实路径后匹配。processMemoryFile 在读取前检查排除结果，因此它影响的是发现链里的实际条目，而非最后包装时删某几句话（A-32）。

原文依据：utils/claudemd.ts:626-637。

条件规则要等到目标路径

frontmatter 的 paths 被拆成模式；末尾 / 被去掉，以适应 ignore 库的目录匹配。空集合或全部 视作无条件。扫描 rules 目录会递归处理子目录与符号链接，再按条目是否有 globs 分出条件和无条件两组。frontmatter 是加载条件，去掉后不会作为普通正文指令发出（A-28）。

真正匹配时，Project 以所属 .claude 的上一级目录为基准；Managed/User 以 originalCwd 为基准。目标转为相对路径，空路径、.. 逃出基准和绝对路径全部返回 false，剩余调用 ignore 匹配。不是任意一份 paths 模式都对同一字符串判断；来源决定坐标原点，跨驱动器等结果也要先挡住（A-33）。

延迟加载入口先检查目标在允许工作路径中，随后装 Managed/User 条件规则，再走 CWD 到目标的嵌套目录，最后补根方向到 CWD 的条件规则。前两类无条件指令已在初始加载里出现，最后一段就只取条件项。注释明确要求保留这个顺序；过滤项目/本地条目的实验开关还在这里再检查（A-34）。

原文依据：utils/attachments.ts:1777-1862。

嵌套目录的无条件扫描和条件扫描使用分开的去重集合，防止前一次处理路径后让后一次匹配被跳过。这里的问题不是“规则文件能否读到”，而是同一文件已经被解析却尚未满足本次目标条件。若让去重同时承担两种含义，就会把未注入的候选误算为已消费（utils/claudemd.ts:1240-1318）。

同一个路径有几种去重含义

扫描目录用 visitedDirs 防止递归重复，解析文件用 processedPaths 防止重复导入，已注入上下文用 loadedNestedMemoryPaths 保持会话内记录。三者都像集合，但对象不同：目录、已处理文件和已发送的指令。发生某个条目“没有再出现”时，应先找是哪一层做了返回，不能只看一个 has(path) 就把它叫已经加载（utils/claudemd.ts:697-778、utils/claudemd.ts:614-685、utils/attachments.ts:1709-1775）。

规则扫描对普通目录项使用 Dirent 方法，符号链接才额外 stat；目录会继续递归，只有文件且扩展名 .md 才处理。不存在、不能访问或不是目录的 rules 路径返回空集合，其他错误仍抛出。空结果可能代表来源下没有规则目录，也可能代表本次无法读取；判断模型没收到规则时，要把扫描结果与调用来源一起查（utils/claudemd.ts:697-778）。

处理后的指令怎样关联文件工具读取状态，已在前一节的双版本记录说明；具体部分视图拒绝交给第 8 章。这里仅跟踪附件使用的缓存对象，避免把注入记录和读取记录归成同一个去重集合（utils/attachments.ts:1709-1775）。

加载原因也不能混着记。带 globs 的文件用 path_glob_match，含 parent 的导入用 include，其他嵌套条目用 nested_traversal；这些原因由具体条目形态选出。它们记录的不是模型决定“这句更重要”，而是宿主在什么条件下把材料放进上下文。同一文件路径的出现，至少还要附着来源类型、内容是否处理以及本次触发目标，才能重现加载事件（utils/attachments.ts:1709-1775）。

初始文件计算又被 memoize。clearMemoryFileCaches 与 resetGetMemoryFilesCache 的区别已经在第 2 章解释，本章只保留落点：前者改变下一次能否复用结果，后者还准备新的 InstructionsLoaded。文件遍历顺序不会因为这个重载原因自动反转，条件规则也不会因 reset 就全改成无条件。缓存事件与发现算法是相接的两层，需按函数参数核对（utils/claudemd.ts:1042-1086、utils/claudemd.ts:1088-1130）。

从文件读取到附件

memoryFilesToAttachments 先查 loadedNestedMemoryPaths，再查 readFileState，生成 nested_memory。注释解释，读取状态是 100 项 LRU，条目会淘汰，所以不能单靠它保证指令只注入一次。转换后的磁盘内容保留为 rawContent，读取状态带 isPartialView；InstructionsLoaded 原因区分路径匹配、导入与嵌套遍历。附件最后成为带来源的 meta 用户消息（A-35）。

到此，CLAUDE.md 的覆盖层有了具体形状：来源开关决定谁参与，目录与导入决定顺序，frontmatter 决定何时加载，非淘汰集合决定是否再注入，而覆盖默认行为仍由包装文字要求模型遵循。权限规则的收集是另一套逻辑，不能从这里的文件顺序推断 deny 被后文件覆盖（utils/settings/constants.ts:3-22、utils/permissions/permissions.ts:213-231、utils/permissions/permissionsLoader.ts:116-134）。
