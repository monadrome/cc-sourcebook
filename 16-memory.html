E · 上下文与记忆预算第 16 章

从当前会话笔记到跨会话记忆

最后一章从 services/SessionMemory/sessionMemory.ts:76-93、services/SessionMemory/sessionMemoryUtils.ts:18-36、services/SessionMemory/sessionMemory.ts:134-181、services/SessionMemory/sessionMemory.ts:240-298、services/SessionMemory/sessionMemory.ts:357-375 的会话笔记走到 memdir/paths.ts:21-55、memdir/paths.ts:79-90、memdir/paths.ts:95-150、memdir/paths.ts:152-205、memdir/paths.ts:223-235 的持久目录。关键区别不在名字，而在三个决定：哪种材料值得留、谁能写、下次怎样进入上下文。下面逐层检验这些决定，避免把“目录里已经有记忆”当成“后台正在更新”，或把“本地已删除”当成“共享服务已经遗忘”。

会话笔记的触发还受当前工作阶段约束

会话笔记并不跟随自动记忆的默认开关。它先有自己的 gate，而且读取缓存配置；这里的立即返回只是避免等待配置，并不授予抽取权限。先看这一入口，才能解释为什么有持久目录的会话仍可能不维护笔记（E-20）。

原文依据：services/SessionMemory/sessionMemory.ts:76-93。

默认 false 与 may be stale 同时出现，说明“未运行”可能来自功能选择，而不是没有可记内容。阈值配置回答的是开启后何时更新，无法倒过来使这个 gate 变成 true。下一块配置因此应按调度参数读，不当启用证据。

原文依据：services/SessionMemory/sessionMemoryUtils.ts:18-36。

这里量的是当前窗口及其增长，不是累计调用消耗。大量重复工作未必产生相应窗口增长；反过来，一段很长的用户材料可能增加窗口，却没有增加工具调用。源码分别保留这两种量，后面的布尔式才决定它们怎样配合。

原文依据：services/SessionMemory/sessionMemory.ts:134-181。

增长条件在两个分支里都必须满足，工具次数却可由自然停顿替代。因此，三次工具调用不会单独触发抽取，“没有工具调用”也不是无条件记笔记。真正的例外是：窗口已有足够新材料时，可以在安全停点更新，不必为了凑次数再调用工具。

原文依据：services/SessionMemory/sessionMemory.ts:240-298。

远端配置零值不会把门槛清零，配置只初始化一次；hook 执行时则重新查缓存 gate，并要求 querySource 完全等于主线程名称。配置稳定与功能是否运行由不同判断承担。还要再问一次：这个 hook 在当前环境中是否已注册？

原文依据：services/SessionMemory/sessionMemory.ts:357-375。

自动压缩关闭或远程环境会在注册前返回，而 gate 在执行时懒检查。这是两道不同入口：注册过不等于每轮抽取，执行 gate 开了也无法补回一个没注册的 hook。笔记服务当前压缩的用途，在这条注册依赖上比一个 memory 名称更明确。

fork 的权限限定了笔记能改哪里

调度只决定何时运行，fork 参数才接上编辑环境。读取状态单独传入而共享缓存安全参数，意味着后台需要既能编辑已知文件，又不直接变更父上下文的状态；“只做笔记”接下来还有实际回调约束（E-21）。

原文依据：services/SessionMemory/sessionMemory.ts:309-325。

独立读取状态解决编辑前置材料，canUseTool 决定操作范围，两者不能互相替代。即便笔记正文完整摆在 prompt 中，工具仍须通过回调；反过来，allow 也不自动补齐编辑所需的读取状态。

原文依据：services/SessionMemory/sessionMemory.ts:457-495。

路径是字符串完全相等，不是“在笔记目录里都可以”；工具必须是 Edit，新建别的文件或改同目录资料仍被拒绝。成功抽取后的游标还等到末尾无工具调用才更新，维护的是保留消息的配对关系。笔记写完和历史可以安全切开，不被当成同一个时点。

笔记模板的来源排除与标题保护见第 6 章（services/SessionMemory/prompts.ts:43-80、services/SessionMemory/prompts.ts:111-129）。自定义 prompt 能替换文字，却不在这个回调里放宽文件范围；内容协议与操作权限各自留下了边界。

开关与目录覆盖接受不同来源

自动记忆的 settings 排在环境判断后。项目配置不能盖过显式环境选择；尤其是名为 DISABLE 的变量取显式 falsy 时，会提前开启并跳过后面的 SIMPLE、远程持久目录和 settings 分支。这比笼统说“bare 总关记忆”更窄（E-24）。

原文依据：memdir/paths.ts:21-55。

这段先判断“能不能用”，没有决定“存到哪里”。环境选择覆盖了功能开关，也不等于给所有路径来源同样的信任。下一块先选择基础目录，其后才处理完整目录的覆盖，两个层级不能混读。

原文依据：memdir/paths.ts:79-90。

remote 变量在此直接提供 base，而不是交给下面的完整路径覆盖校验。当前引文不能证明每个目录入口都走相同验证；完整目录的安全规则，应准确限定在 validateMemoryPath 的调用者上。否则会把一处检查外推成所有来源的保证。

原文依据：memdir/paths.ts:95-150。

拒绝根目录、近根和可退到 home 的 ~ 余部，不只是处理格式好不好看。它避免一个过宽目录让路径范围判定接受原本不该归为记忆的文件；注释明确把校验与读写豁免联系起来。随后哪些配置有权提供这个目录，就成为授权问题。

原文依据：memdir/paths.ts:152-205。

项目可以通过前面的 autoMemoryEnabled 选择是否使用功能，却不能用 projectSettings 选择写入根。这里信任的是特定覆盖来源，不是整个 settings 系统。canonical git root 又让多个 worktree 指向同一默认存储身份，持久目录故意不随临时工作目录逐个分裂。

原文依据：memdir/paths.ts:223-235。

实际路径先取完整覆盖，再走项目默认，memoize 的键却仍是 projectRoot。目录解析、项目身份和会话 cwd 是不同概念；不能仅因切到 worktree 就推断它得到新的私人记忆。至此才有可读取的入口，接着还需限制入口装入多少内容。

入口是索引，也会裁掉正文

二百行不能限制超长单行，命名为 BYTES 的第二个限制实际又用字符串 length。这里最重要的是确定被限制的对象：入口内容经 trim 和裁切，再追加告警；数值不等于最终包装后上下文的严格上限（E-25）。

行裁切和长度裁切串行执行，统计告警却依据原始长度；模型可能只看到部分索引，仍被告知为何裁掉。长单行没有可用换行时还可直接在长度边界切开。“入口一直加载”因此只表示尝试注入这份索引，不表示每个指针都被看见。

保存说明让主题文件放正文，入口只放简短指针（memdir/memdir.ts:218-257、memdir/memoryTypes.ts:258-271）。这与裁切不是两条互不相关的规范：细节若直接挤进入口，就与发现其他主题的指针争同一份有限材料。接下来类型规则决定哪些信息值得占这个位置。

类型分类与保存标准不是同一道检查

类型解析故意允许缺失或未知 type 的旧文件继续工作。类型集合在这里帮助识别，却没有把所有非枚举文件判为不可读；“四种类型”不能解释成磁盘内容必须严格满足四种新格式（E-27）。

原文依据：memdir/memoryTypes.ts:14-31。

返回 undefined 保留了兼容阅读路径，而保存提示词仍教模型按已知类型组织新材料。解析器能接受文件，与模型该怎样写文件之间有明确差别，下一块文本负责后一个问题。

原文依据：memdir/memoryTypes.ts:113-178。

feedback 同时保存纠正和被用户确认的做法，避免把未来协作仅写成禁令清单；project 要求保留原因，并把相对日期变成绝对日期。reference 存寻找当前信息的指针，而非复制远端快照。分类在这里安排未来使用方式，不只是给检索附一个标签。

保存标准又会排除看似符合类型的内容。尤其是 project 不是“所有项目事实”，仍须排掉代码或 git 能重建的材料；即使用户说 remember，也要按这份提示判断保存对象（E-28）。

原文依据：memdir/memoryTypes.ts:180-195。

这与“用户要求就记住”存在实际张力：原句限制直接保存 PR 列表、活动摘要等，要求找其中非显然信息。它没有取消用户请求，而是重新界定应留下的内容。这里是提示词的取舍，不能误写成文件工具在运行时检查了每条记忆是否可由代码推出。

回忆也不是保存后永远启用。用户要求忽略记忆时，文本要求连引用、比较和提及都避免；入口已加载与内容允许影响当前任务，被分成了两个问题（E-29）。

原文依据：memdir/memoryTypes.ts:197-222。

这是模型如何使用材料的限制，不是磁盘删除操作。“忽略本轮记忆”和“忘记这条持久信息”应分别解释，否则一句忽略请求会被扩大成破坏存储。真正使用旧内容时，还要与当前观察核对。

原文依据：memdir/memoryTypes.ts:224-256。

当前源码和环境优先于历史记忆，具体文件、函数或 flag 的推荐要验证存在。保存标准排除可重建快照，召回标准又要求检查现状，两者共同阻止旧状态悄悄替代现在的证据。reference 的“去哪找”在这里也比“曾经是什么”更符合用途。

检索先删候选，再让模型选

扫描器先按修改时间收窄到二百份，相关性模型没有机会从整棵目录任意发现内容。前三十行的描述是否足够，因而影响候选呈现；这是元数据筛选与后续语义选择接在一起的接口（E-30）。

原文依据：memdir/memoryScan.ts:13-94。

代码先读小范围再排序，并非只对最早挑出的二百份做 I/O；注释给的是减少重复 stat 的理由。结果上限与扫描成本不能混为一谈。空列表也可能是读取失败，不能用它宣称用户没有记忆或记忆无相关性。

模型选择的目标是明确有帮助，而不是见到名字相近就塞满五个位置。活跃工具的常规参考可跳过，警告和已知问题却保留；相同关键词在两类材料里有不同意义（E-31）。

原文依据：memdir/findRelevantMemories.ts:18-24。

这个例外把“现在已会调用”与“现在更需要看风险提示”区分开。它收窄的只是模型推荐规则，没有将风险文件设为必选；输出结构和文件白名单还要由下一段代码处理。

原文依据：memdir/findRelevantMemories.ts:77-141。

schema 只要求字符串数组，没有 maxItems；白名单也只剔除不在候选里的文件名，并不证明模型遵守五项限制。硬数量边界要在消费这些推荐的附件层寻找，不能用前面的文字要求或 JSON 形式代替它。

原文依据：utils/attachments.ts:2226-2242。

这里才在跨目录结果汇总后 slice 五个，并过滤已经读取或展示的路径。它约束本次注入，而非每个选择器调用各自五项的总和。另一次引用同一消费点，接着说明索引实验如何把入口替换成这条路径。

换注入方式，并没有把全部预算合并

索引关闭不是自动记忆关闭。filterInjectedMemoryFiles 只按实验 gate 去掉 AutoMem/TeamMem；人工指令文件仍在集合里，相关文件又可能经另一种附件进来（E-32）。

原文依据：utils/claudemd.ts:1136-1151。

默认 false 时沿用入口索引；true 时改用相关性路径。下面的限制要按新路径计算，不能直接复用入口 MEMORY.md 的长度帽，因为被注入的现在是主题文件正文。

注释里的五份乘四KB只是正文规模说明。工具结果预算不覆盖这些 system-reminder 附件，故另加字节限制；但它尚未计入告警和来源头。文件选择、正文读取和消息包装仍是三步。

原文依据：utils/attachments.ts:2196-2242。

多个目录并行选择后才合并截数，agent 被点名时还会按其记忆目录隔离。前面索引是否注入的 gate 不负责这些隔离与去重；看到索引消失，不能据此判断哪个 agent 的文件会被召回。

原文依据：utils/attachments.ts:2268-2321。

读取正文先裁切，返回内容再追加完整文件路径的告警并另给 header。因此4096字节不是最终附件整段硬帽；源码保留回查路径，是允许读者发现“这只是部分内容”的补偿。裁掉的后半段并未凭空保存在模型可见文字里。

原文依据：utils/attachments.ts:2355-2404。

预取还要求真实用户消息、多词输入和会话预算；meta 注入不作为新的查询意图。即使索引已按 gate 关闭，本轮仍可能没有预取材料，比如只有单词输入。关闭入口与本次一定有替代附件并不等价，这是切换协议里应保留的空结果路径。

抽取的运行权与记录去重另行处理

有自动记忆功能，不等于每个合格轮次都启动抽取。内部运行先节流，再扫 manifest；缓存共享要求工具列表稳定，真正操作范围交给 canUseTool。这里先展示执行体，下一块再看包在它外面的启用判断（E-33）。

原文依据：services/extractMemories/extractMemories.ts:362-431。

五轮限制是执行器给 fork 的上限，不是提示词估计“两到四轮”已经实现。manifest 放在节流之后，跳过的轮次不必扫目录；成功才前进的游标又给失败保留重试材料。入口本身还有一套独立 gate。

原文依据：services/extractMemories/extractMemories.ts:527-568。

默认关闭抽取、关闭自动记忆、子 agent 或远程环境都在 runExtraction 前返回；当前已有抽取时只保存最新待处理上下文。这说明默认开启目录功能与默认开启后台执行分离，也避免把多个同源请求说成各起一份独立 fork。

主 agent 的直接写调用还可让后台认为同一范围已处理。这里判断的材料是 assistant tool_use，不是目录当前内容，也不是“用户是否提过记忆”（E-34）。

原文依据：services/extractMemories/extractMemories.ts:112-148。

函数不在此消费对应 tool_result，所以“写过”应准确读成调用记录命中，不能外推为已确认写入成功。这是当前证据中一个重要范围限制；后台怎样响应这个布尔结果，要继续看游标处理。

原文依据：services/extractMemories/extractMemories.ts:329-360。

命中后不仅跳过 fork，还把游标推进到范围末尾，不会下轮把这段重新当新材料。去重判断因此影响后续覆盖范围，而非只省一次运行。它以调用记录作依据，与上一段“抽取失败保留游标”走不同分支，不能合称所有失败都自动重试。

读取许可也不等于可以把读到的全部内容存进去。权限回调能放 Read/Grep/Glob，文本却限制只从最近消息抽取、不得继续查源码；这两层分别限制操作能力与材料用途（E-35）。

原文依据：services/extractMemories/extractMemories.ts:166-222。

与会话笔记的单文件 Edit 相比，这里可广泛读、在记忆范围内写，但 shell 仍须 parse 成功且 isReadOnly。REPL 的 allow 又靠注释所说的内部原语回调重新检查。不能把“包装器允许”解释成绕过内部写入限制，也不能用可读范围替文本的保存标准授权。

团队共享给同一类型再加一道范围

团队记忆依赖自动记忆，却没有沿用它的默认 true；存在团队目录也不足以证明共享启用。先看父开关和团队 gate，再谈每种类型放哪一边（E-37）。

原文依据：memdir/teamMemPaths.ts:66-94。

这个依赖只回答功能能否运行，不决定一份 feedback 是否可共享。下面类型规则在已启用的功能内继续细分，用户画像不能因为整个项目合作就自动变成团队资产。

原文依据：memdir/memoryTypes.ts:37-106。

user 必须私人；feedback 的团队共识例外、project/reference 的通常范围都由用途而非文件名决定。关键词“通常”保留了模型判断，不能把它译成解析器自动搬目录。写入地点选好后，每个范围还需自己的入口。

原文依据：memdir/teamMemPrompts.ts:43-93。

两份索引分别维护，使私人材料不必靠共享入口发现；禁止凭据入团队是内容要求，不是目录授权已经完成的工作。随后 dispatch 又证明，团队模式不会无条件叠在所有记忆提示上。

原文依据：memdir/memdir.ts:448-473。

实际装配先检查团队条件，再返回普通自动记忆提示。文本中的保存体系由这次分支选择，不能因证据库里两份说明都存在就认为模型同时收到它们。共享材料的写入还要再看路径与内容检查。

能写进目录，不等于能写任何内容

字符串范围检查拦明显越界，真实路径检查拦符号链接逃逸；后者补的是前者无法表达的目标位置。两步同在写路径校验里，不靠模型自报“这是团队目录”（E-38）。

原文依据：memdir/teamMemPaths.ts:222-256。

这里证明最终目标仍落在 team 下，却没有证明正文适合共享。路径合格只让内容到达下一道检查，故“已有记忆写权限”不能覆盖凭据禁令。

原文依据：services/teamMemorySync/teamMemSecretGuard.ts:3-44。

秘密 guard 在 TEAMMEM 下查看拟写文本，命中直接返回拒绝说明。它阻止这一内容写入，不是撤销目录长期许可。上传层还会再扫，因为它不能假定每个本地文件都曾经过同一个工具验证入口。

原文依据：services/teamMemorySync/index.ts:562-617。

上传跳过整文件而不是只删匹配片段；本地存在因此不表示已同步到队友。只纳常规文件、跳大文件也会让两边集合不同。前面的保存指令、写入验证与上传选择对不同对象作判断，不能压成“team 下所有文件自动共享”。

同步契约让删除与冲突有不同后果

服务注释同时给 pull、push 与删除语义：两边都叫同步，不代表冲突时用同一种优先级。先保留这个契约，后面的客户端条件再解释何时会调用它（E-39）。

原文依据：services/teamMemorySync/index.ts:1-25。

pull 按 key 服务端胜出，push 只 upsert 差异项，没有发送的 key 保留。删除本地文件因此不会表达远端删除；下次拉取还能恢复。用户要求“忘掉团队记忆”时，不能把一个本地 rm 的成功当已完成远端遗忘。

原文依据：services/teamMemorySync/index.ts:149-161。

OAuth scope 在这里是一种服务身份要求，不是任意 token 非空就够。它也不替代类型范围和秘密检查：身份能访问共享服务，与这份材料值得上传仍是不同许可。

原文依据：services/teamMemorySync/watcher.ts:252-319。

watcher 先拉取再监听，又查构建特性、团队开关和 GitHub 仓库。单纯开目录监听不足以复现同步。接下来冲突重试还要解释为何 push 可保留本地编辑，而前面的 pull 却强调服务端胜出。

原文依据：services/teamMemorySync/index.ts:869-888。

冲突重试先刷新服务端校验和，再重算本地差异；本地当前编辑仍可覆盖同 key，但不合并文件正文。与 pull 的服务端优先并不矛盾：它们是不同操作方向。与此同时，“本地删除”没有作为 key 删除指令加入，所以这个重试也不能替删除传播补出一个保证。

长驻日志与共享索引并不叠加

日记分支把当轮新材料改写到按日追加的日志，让夜间流程维护主题与索引。值得留意的是日期来源：注释说缓存段不在午夜失效，要靠 date_change 附件；正文却让模型从 currentDate 取日期（E-40）。

原文依据：memdir/memdir.ts:318-370。

这是一处必须保留的文字张力，不能替源码选择一个统一说法。上下文日期有更新附件与静态前缀两个位置，作者注释明确说后者有意留旧；当前指令如何指代“今日”，不能只照正文中的一个标识符解释。另一方面，追加日志和改索引本就是两份不同写职责。

原文依据：memdir/memdir.ts:419-438。

KAIROS 先返回，所以不会继续叠加团队提示；注释说追加日志方式不能与双边共同读写索引直接组合。拥有同一持久目录并没有消除协议差别。全书最后回到这个判断：要解释一种记忆行为，先找到当前选择的保存和召回协议，再核对授权、内容与同步，不用一个 memory 总标签替代各条分支。
