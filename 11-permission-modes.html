D · 权限与安全边界第 11 章

权限模式与分类器的边界

第 10 章的内层判定留下 ask，这章看 utils/permissions/permissions.ts:503-549 怎样转换它，再追 utils/permissions/permissionSetup.ts:597-646 的模式状态与分类器输入。值得分开的至少有三件事：模式名字在类型中合法、当前会话可进入该模式、这次动作由分类器放行。前两者不会自动证明第三者。

类型集合与可用性不是同一张表

模式类型、可选集合和模板来源是不同判断。源码保留auto的外部模板分支，就不能将内部联合类型的名字解释成只供内部用户；当前运行时输入集合还由构建条件收窄（D-36）。

原文依据：types/permissions.ts:16-36。

UI 轮换顺序另有实现，内部用户会跳过 acceptEdits 和 plan，dontAsk 不在普通轮换里（utils/permissions/getNextPermissionMode.ts:38-78）。类型允许的值、CLI/设置可选集合和交互轮换各回答不同问题。本书不展开 UI 颜色，只沿可用性和判定查安全条件，避免把界面上看见一项当成它的全部语义。

联合类型只是静态穷举，运行时数组才决定可验证的输入。auto因此可以在类型里存在而在没有feature时被数组排除；“内部联合包含auto”本身不是用户可选的证据。

原文依据：utils/permissions/yoloClassifier.ts:54-78。

分类器模板的选择又按USER_TYPE和forceExternalPermissions分支，证明构建内同时保留外部与内部文字，但不替任何发行构建确认开放范围。模式名称、模板来源和gate应分别记录。

auto 的配置 enabled 有 enabled、disabled、opt-in 三态，缺失默认 disabled，注释把 disabled 描述为事件响应断路器。它决定能否进入或显示 auto，当前分类器是否激活还另有状态（D-30）。

bypass 可用性要求 CLI 模式或允许危险跳过的意图，并同时未被远端 gate 和 settings disable 禁用。CLI 初始化按候选顺序选择，被禁的 bypass 跳过后取下一个有效项；无结果才回 default。旧标题说总降级 default 过强，D-64 的完整循环保留了这个差别。

可用性布尔值把“有危险意图”与“组织/设置允许使用”合在一起；同样的bypass字符串若没有前一个意图，标志仍可能为false。它是进入模式的门，不是对已经在模式中的每次调用重新执行完整权限检查。

循环跳过被禁候选后保留notification，并选择下一个有效模式，只有候选耗尽才default。这里的回退是一个有序选择器，不是单一的降级函数；使用CLI和settings同时提供候选时，顺序本身也会改变用户落入的模式。

远程环境对 settings.defaultMode 另限 acceptEdits、plan、default，注释说明防止静默授予全权限。启动后的 bypass 检查一处会退出进程，另一处更新权限上下文；一次性标志和登录重置也有具体范围。不同入口的“禁用”不一定同样表现，不能只看 gate 名称就描述为统一回默认（utils/permissions/permissionSetup.ts:743-759、utils/permissions/permissionSetup.ts:1407-1431、utils/permissions/permissionSetup.ts:1262-1267、utils/permissions/bypassPermissionsKillswitch.ts:49-73）。

模式切换会改规则集合

切模式会改变规则集合与活动状态，不能仅写一个新mode。尤其plan可附带auto，进入和离开侧并非对称的字符串比较；注释要求用实际active状态判断离开，正为避免替代字段滞后（D-24）。

为什么要剥离宽泛解释器许可，危险模式列表的注释有直接理由：Bash(python:*) 等可运行任意代码，会在更早的 allow 处绕过分类器。跨平台清单含解释器、包运行器、shell 和 ssh。这里保护的是规则形状的过宽许可，不是说每次 python 或 npm run 调用都危险（D-55）。

原文依据：utils/permissions/dangerousPatterns.ts:1-42。

plan 可以叠加 auto，但 transitionPlanAutoMode 明确排除 prePlanMode 为 bypass 的情况；这一分支与第 10 章 plan 的 bypass 可用性检查不同。前者决定中途是否激活 auto，后者决定内层结果是否按 bypass 短路。两处字段不能互换，模式名称相同也可能有不同附带状态（utils/permissions/permissionSetup.ts:1502-1511、utils/permissions/permissions.ts:1262-1281、utils/permissions/permissionSetup.ts:930-943）。

gate 异步变化时，verifyAutoModeGateAccess 返回对新上下文执行的变换；源码注释解释，如果闭包拿旧模式，用户等待期间切换会被覆盖。真正处 auto 就恢复规则并回 default；plan 叠 auto 则保留 plan、关闭 auto 并调整 prePlanMode。这是模式状态和规则集合一起修正（D-61）。

变换函数在应用时重读mode，避免异步gate请求完成后用旧上下文覆盖用户刚切换的模式。这里的“踢出”不只是写一个default字符串，还需恢复剥离规则、停auto状态、处理plan的prePlanMode；遗漏任一状态会让后续判定不再符合界面显示。

ask 的外层处理继续区分安全原因

dontAsk 把 ask 转 deny。auto 或激活 auto 的 plan 则先看 safetyCheck 是否 classifierApprovable；不可批准的检查保留交互，无提示环境拒绝。可批准的敏感文件检查继续进入分类器。故 bypass 不可绕过不等于所有模式必须弹窗，安全原因还有一个明确布尔字段（D-38）。

原文依据：utils/permissions/permissions.ts:503-549。

工具自身要求交互的 ask 也不会被 auto 当普通分类候选直接处理。其他快速路径与分类器只作用于走到这里的结果；第 10 章更早返回的整工具 deny 或显式内容 ask 必须按各分支继续核对，不能把 auto 写成取代所有规则的一次模型判断。

分类器没有照搬主对话

分类器所见材料不是主对话的缩短副本，它选择保留原用户文字和工具输入，排除模型自己写的正文。这个选择决定谁的授权说法能成为分类依据，不能用assistant复述替代用户原话（D-51）。

原文依据：utils/permissions/yoloClassifier.ts:297-360。

这条投影限制有具体安全意图，来自注释。分类器确实看到的内容由过滤与工具输入编码决定，不能用模型自己在回复里说“用户已批准”代替原用户文本。下一次 API 错误提到转录过长时，也要按这份投影的大小和模型窗口查，而不直接拿主上下文占用替代。

模板通过构建 require 三个 .txt 文件，本树缺对应目录。装配函数仍可读：external 模板中用户段替换默认，内部模板把默认留在标签之外，用户段追加；allow、soft_deny、environment 分别替换标记。这里只能分析装配语义，不补造模板里的安全规则（D-52）。

原文依据：utils/permissions/yoloClassifier.ts:46-69。

require被feature包住，所以缺失模板限制的是我们审查模板正文的能力，不让装配代码的条件消失。后面的replace仍能说明用户配置是覆盖还是追加，但不能补出默认规则的具体文字。

原文依据：utils/permissions/yoloClassifier.ts:480-525。

external替换与内部追加由模板标签位置造成，而非allow字段名字本身决定。用户写相同配置，在两种模板上可能保留不同的默认规则；这里应据装配注释限定语义，不能将“用户可配置”理解为任何环境都彻底替换默认。

失败结果也分几种

响应 schema 解析失败返回 shouldBlock:true。外层遇到转录超窗，有交互则回确认，无头抛 AbortError；API 不可用又查 tengu_iron_gate_closed，默认 true 时拒绝并给重试指导，另一分支返回原结果。注释称 fail open，但返回的是此前 ask 等权限判定，绝非直接 allow（D-53）。

原文依据：utils/permissions/yoloClassifier.ts:1215-1236。

schema错误先变成shouldBlock，说明解析失败不会被当作一个无意见结果。这个内部分类结果还要到权限外层解释，才能决定是拒绝、人工确认还是保留原判定。

原文依据：utils/permissions/permissions.ts:818-877。

transcriptTooLong是确定性材料问题，交互回确认、无头中止；unavailable又受fail-closed gate影响。返回result的fail open仍是原来的ask等判定，不能跳过用户选择。错误类型而非一个“分类器失败”总标签决定后果。

拒绝次数另有约束：连续三次或总二十次进入回退，成功清连续计数；有头环境把控制交回提示，无头中止。这里不会因模型继续尝试就永远产生新分类请求，实际计数与中止条件独立于拒绝消息中的“请停下”要求（D-54）。

原文依据：utils/permissions/denialTracking.ts:7-45。

连续和总拒绝分别追短期卡住与会话累积，成功只清连续；一两次成功不能将总次数抹掉。达到任一阈值时，后面的处理还要看是否有提示能力。

原文依据：utils/permissions/permissions.ts:995-1029。

有头路径让用户检查转录，无头只能中止；这两种后果与同一个计数条件配对。计数不是对模型意图的判罪，只是避免持续拒绝仍无穷重试的执行约束。

这一章得到的模式语义，是规则集合、active 状态、可用性 gate、转录过滤与失败回退共同组成的行为。接下来还需处理一个 ask 的现实去向：谁能给用户看，谁能替输入，几个异步批准谁先结算。第 12 章从这些交互事件继续。
