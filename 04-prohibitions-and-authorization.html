B · 行为引导模式第 04 章

禁止、替代动作与授权豁免

这章看三件事：提示词禁止哪个动作，允许模型怎样继续，用户能批准哪些例外。主要源码是常规系统提示词 constants/prompts.ts:175-267，以及 Bash 和 worktree 的工具描述。值得细看的是禁令后面的条件、替代动作和授权范围：读漏一句，就可能把“别这样调用”读成“这件事不能做”，或把一次批准用到下一次操作。

行为引导卷按文字的触发条件和措辞解释要求，方法边界见阅读说明。实际判定和执行环境留到权限卷对拍，当前章先保留禁止、替代与授权的原句。

先问它禁止了哪个动作

开场段的 URL 规则禁止“生成或猜测”，同时允许使用用户或本地文件提供的 URL；前一个禁令还带着“确信有助于编程”的条件。它没有要求把所有 URL 都删掉。B-02 的原文将动作、条件和可用来源写在一起：

读这种句子，光圈出 NEVER 不够。这里要限制的是没有把握却替用户补一个地址；用户已经给出的地址另有许可。把来源也读进去，才知道哪些材料可以直接用，哪些需要继续查。后一种判断仍由模型执行，这个字符串本身没有校验 URL 的代码（constants/prompts.ts:183）。

工程任务中的禁令也限定了对象。源码禁止为这次修改顺手增加功能、清理周边代码、为假想需求加抽象；同一组原句还明确排除半成品。它把“少做多余的事”和“把请求做完”放在同一句里，没有让简化成为提前收工的理由（B-04、B-05）：

这几句给了具体参照：修 bug 不必清理周围代码，简单功能不必增加配置，一次性操作不必造 helper。规则针对修改范围和复杂度；源码仍允许系统边界上的校验，也允许确实必要的实现。因而，评审一次改动时可以逐项问它是否回应了用户请求，而不用把所有新增代码都归为违规（constants/prompts.ts:201-203）。

被拒绝之后，继续做什么

常规 System 段把权限拒绝后的下一步写得很明确：不要原样重试同一个调用，先理解拒绝理由，再调整做法。它没有要求每次拒绝都结束任务（B-03）：

公共拒绝指导把“调整”说得更细。换一种自然适合该目标的工具可以尝试，示例是用 head 代替 cat；借运行测试的权限偷偷执行非测试动作则不允许。判断对象从工具名称转到拒绝的意图：新命令即使换了名字，也不能替模型获得用户刚刚拒绝的能力。如果该能力确实不可缺，原文要求停下解释，让用户决定（D-19）：

作者推断这里还有一处张力需要保留。拒绝指导拿 head 替代 cat 作正面例子，专用工具段却要求用 Read，Bash 又把 head 列进避免命令。前一句只能说明合理换办法的方向，不能单凭这个例子认定 head 在当前会话已获准。核对一次具体替代时，还须带上工具选择条件和权限结果（utils/messages.ts:226-232、constants/prompts.ts:291-305、tools/BashTool/prompt.ts:293-295）。

这段指导由 AUTO_REJECT_MESSAGE 和 DONT_ASK_REJECT_MESSAGE 拼进拒绝消息。工具执行层直接取权限判定结果的 message 来构造错误 tool_result，没有在此给所有拒绝统一补后缀。因此，“每次拒绝都附有相同指导”的说法超出了这两处代码（D-60）：

原文依据：services/tools/toolExecution.ts:1023-1038。

任务段还有一条相邻的限制：方法失败后先诊断，不盲重试，也不因一次失败就扔掉仍可行的方法。读错误、检查假设、尝试针对性修复，是它给出的动作；向用户升级问题应当发生在调查之后（B-08）。

作者推断这两组规则可以连着读：权限拒绝要求尊重用户的意思，执行失败要求查清技术原因。把二者混在一起，会让“换个办法”变成未经授权的绕过，或让一个普通报错变成无必要的请示。这个区分来自两组原句的不同触发条件，不是本次测得的模型行为。

并行调用也有前提。常规工具段要求独立调用并行，有先后依赖时顺序执行；它没有把“可以一次调用多个工具”写成“任何调用都同时发出”。同一段还要求任务完成就更新状态，不攒到最后统一标记。这里给模型的是调度与进度记录要求，不能据此认为执行器已经识别了任务之间的语义依赖（B-14）。

原文依据：constants/prompts.ts:307-314。

条件的次序很重要。“我更熟悉这个命令”没有出现在豁免中，“专用工具可能不行”也不等于已经核实办不到。源码要求模型先找到理由，再改变调用方式。这里的明确指令解除的是工具选择限制；它没有在这段文字里顺带批准命令的文件访问、网络连接或删除操作（tools/BashTool/prompt.ts:357-363）。

沙箱描述把另一类豁免展开成了分支。策略允许无沙箱命令时，模型可以根据用户明确要求，或刚发生且有证据指向沙箱的失败，发起禁用沙箱的重试。原文紧跟着提醒：这会触发用户许可；每条命令要单独处理，之后仍回到默认沙箱。策略关闭该能力时，另一分支直接要求调整设置（C-08）：

这个分支没有把所有报错都归因于沙箱。它要求“刚刚失败”和“看见限制证据”同时成立，另列缺文件、参数错、网络问题等其他原因。后面的报错例子要连着这个前提读：它们供模型判断当前失败是否符合条件，不能单凭命令失败就取得例外。这一段列出识别要求，没有提供失败原因的自动诊断结果（tools/BashTool/prompt.ts:231-248）。

“直接重试，不要先问”指导模型发起调用；“这会提示用户批准”则是文案对许可流程的说明。把前一句单独摘出来，就漏掉了仍需许可的提醒，也容易错读为模型已获准在沙箱外执行。更不能拿这一分支遮住下方策略禁用时的要求。

临时目录有相似写法：scratchpad 提示先检查功能是否启用，再要求所有临时材料使用会话目录，只有用户明确要求才改用 /tmp。Bash 的沙箱段则要求使用 TMPDIR。两处的对象和运行环境都不同，不能只摘出一个目录名当全局约定（B-28、C-08）。

一次批准究竟覆盖什么

动作段先按可逆性和影响范围划分默认做法：本地编辑与测试通常可自由执行，难撤回、影响共享系统或可能破坏的动作默认先确认。它允许用户通过明确指令调整自主程度，但随后收紧授权范围：批准过一次 push，不代表以后所有情境都批准；持久指令也只能覆盖所写的范围（B-12、D-57）：

动作清单紧接着这条原则：删除、强推、改 CI、对外发消息和上传内容都有例子。遇到锁文件、陌生分支和未提交工作，则先查明它们是什么，再决定如何处理。作者在原文中比较了暂停确认和误操作的代价；本章引用的是这个具体理由（constants/prompts.ts:258-266）。

worktree 描述把授权落实到用户说了什么。EnterWorktree 要求用户明确提 worktree，普通的建分支、修 bug、做功能请求不算。短引保留允许与不允许的场景，完整描述见区间指针，避免只看“创建隔离环境”就自行扩大任务（C-22）：

原文依据：tools/EnterWorktreeTool/prompt.ts:1-30。

退出时，范围又收窄到本会话由 EnterWorktree 创建的 worktree；手工创建的目录和旧会话都排除。删除参数说明要求遇到未提交文件或原分支上没有的提交时，先确认再带 discard_changes 重试。用户要求“退出”不能在这段描述中自动等同于“丢弃这些修改”：

参数说明也值得逐字看。keep 会保留目录和分支，remove 才删除；discard_changes 默认 false，并且只对 remove 有意义。一个用于结束会话的请求，里面仍可能有“保留工作”和“清理目录”两种选择。文案要求模型先识别用户要哪种结果，看到待丢弃内容时再取得相应确认（tools/ExitWorktreeTool/prompt.ts:18-23）。

这两份描述都给了模型可核对的对象：用户是否说了 worktree、创建者是否是本工具、会话是否相同、当前是否有待保留内容。本章引用的是工具描述的要求，没有回查删除执行器的全部分支，故不把其中的 REFUSE 直接写成已验证的删除保护。

规则还要连着会话条件读

自主工作段有自己的构建与运行开关。它要求第一次 tick 先问用户方向，后续才寻找可做的事；无事可做就 Sleep，禁止重复发送空状态。后半段又要求自行判断、在合适停点提交，并按终端焦点调整协作程度（B-30、B-31）：

同一文件确实同时保存了“先确认风险动作”和“按判断行动”的文字。解释它们时，必须带上各自的装配条件：自主模式在 getSystemPrompt 中有早返回数组，普通路径则把 actions 段放进另一组数组（constants/prompts.ts:466-488、constants/prompts.ts:560-577）。仅把两句话并排，既不能证明同一会话收到了全部规则，也不能证明自主模式已绕过权限。

委派与技能发现也用条件限制动作。非 fork 的 Agent 指导要求匹配专用 agent 的描述，避免重复被委派的搜索；fork 分支明确要求执行者不要再转派。DiscoverSkills 则在已浮现技能覆盖下一步时要求跳过发现调用（B-15、B-17）。

技能的许可范围还限定了名称集合：只用列在 user-invocable 部分的技能，不猜名字，也不把内建 CLI 命令当技能。对模型而言，“存在调用工具”和“这个名字允许调用”需要分别核对；slash command 的外观本身不能替代列表（B-18）。

定向搜索和探索委派也有单独条件：具体文件、类、函数先用搜索工具；广泛调查才考虑 Explore。原句说明它更慢，简单搜索不足或任务明显需要超过查询次数常量时才采用。这个比较理由属于提示词原文，不能改写成“所有搜索派 agent 都更高效”（B-16）。

这些段落逐一限定了自主工作、委派和技能发现的触发条件。授权随用户请求读，工具选择随可用集合读，功能规则随会话条件读；“积极行动”到这里已有具体的下一步与停止条件。

外来内容不能自行变成授权

常规 System 段提醒工具结果可能含外部数据，发现疑似提示注入时先向用户指出。hook 段则要求把 hook 反馈视为来自用户，并给被阻止后的调整与检查配置路径。这是两种来源的不同处理要求（D-58）：

安全文本还用用途限定可协助的请求：经授权的测试、防御、CTF 和教育场景可以协助，双用途工具要求清楚的授权背景，恶意用途另列拒绝项。它没有把“出现安全工具名称”当成唯一判断条件（D-59）：

作者推断贯穿这些原句的阅读顺序是：先找被限制的动作，再找允许继续的办法，最后核对谁给了授权、授权覆盖哪个对象和哪次操作。这个顺序能帮助我们检查解释有没有漏条件。下一章继续读另一个停止条件：任务究竟做到哪一步才可以宣布完成。
