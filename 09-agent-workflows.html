C · 工具提示词第 09 章

委派、计划与任务协作的调用流程

这一章从 tools/AgentTool/prompt.ts:15-46、tools/AgentTool/prompt.ts:59-78、tools/AgentTool/prompt.ts:190-218、tools/EnterPlanModeTool/prompt.ts:4-64、tools/EnterPlanModeTool/prompt.ts:93-136、tools/EnterPlanModeTool/prompt.ts:160-170 和 tools/TeamCreateTool/prompt.ts:1-63、tools/TeamCreateTool/prompt.ts:74-113 看工具描述怎样安排多人或多阶段工作。它们值得放在一起，因为委派、审批、状态更新与消息投递都要求前后步骤接得上；发出工具调用并不自动等于对方收到了足够材料，或用户看见了可批准的计划。

可用 agent 类型先被筛选

委派之前先要形成一个可信的候选集合：agent名能被模型看到，不能同时说明它适合当前任务或具有实现能力。描述生成器把工具限制与类型限制分开处理，正适合检验这两个问题（C-14）。

原文依据：tools/AgentTool/prompt.ts:15-46。

允许列表减拒绝列表是在描述生成时完成，说明“被允许”首先是模型看到的候选集合。实际工具权限和执行时输入还未发生；类型过滤也不会替代后面的工具池和权限检查。委派协议从一开始就有两层可见性。

列表的来源是第一层；描述里列出哪些使用场景是第二层。模型可能看到一个类型，却被说明文字要求在小范围搜索时不要派它。可用和适用必须分别判断。

原文依据：tools/AgentTool/prompt.ts:59-78。

coordinator只得到共同核心文本，普通模式才追加不适用情境和说明。相同Agent工具名因此可能收到不同长度的微型harness，这种差异来自调用者模式，不是agent定义自身变化。

原文依据：tools/AgentTool/prompt.ts:190-218。

因此，任务“适合 agent”仍需核对具体类型能不能写文件、有哪些工具。TeamCreate 的文本明确禁止把实现交给只读 agent，要求先看 Agent 描述中的能力（tools/TeamCreateTool/prompt.ts:1-63、tools/TeamCreateTool/prompt.ts:74-113）。委派选择不能只靠名字像研究员或工程师；当前列表与工具限制才是交接目标的实际输入。

未开启 fork 的使用说明把明确路径和小范围搜索留给直接工具，要求短 description、向用户总结不可见结果、按是否依赖结果选择前台或后台。后台结束靠通知，不主动 sleep/轮询；交接必须说明是研究还是写代码，继续 agent 用 SendMessage。任务边界和等待方式同时写进了这份描述（C-15）。

原文依据：tools/AgentTool/prompt.ts:220-249。

前台/后台的选择其实是结果依赖的选择：后台不能立即提供主任务必需的中间值，通知才是它的返回通道。短description要求则约束交接的输入大小，不能把“用户看不到原始输出”当成“可以省略结论”。

委派说明和等待说明共同构成返回协议：描述谁做什么，通知何时回来，SendMessage如何继续。任一项缺失都可能让主任务既没有结果也没有可复述的结论。

原文依据：tools/AgentTool/prompt.ts:251-287。

teammate上下文还会删除不适用参数说明，说明同一个文本生成器会根据接收者裁切协议。裁切不是删掉执行能力，而是删掉当前接收者不该使用的交接入口。

fork 的交接与上下文不同

fork 分支把不值得保留中间输出作为使用情境，要求等通知，不偷看输出文件，不预测结果；fresh agent 则要求完整交代目标、已有发现、排除项、判断背景与所需回应长度。它还禁止把“理解用户任务”直接交给子 agent，说明调用者应先确定自己的请求（C-16）。

原文依据：tools/AgentTool/prompt.ts:80-113。

fork把“不要偷看输出文件”与“等待通知”放在同一组规则中，限制了调用者从旁路重建结果；fresh agent的背景字段则让新执行者可以在没有原始上下文时独立判断。两种形式都在减少中间状态泄漏，但交接材料的颗粒度相反。

fork依赖主线程保留的任务目标，fresh agent依赖调用者重新写出的背景；两者都把“已有原始上下文”作为不同的资源。选错形式的结果不是只多几句提示，而是子任务可能无法判断自己应交付什么。

（原文见 tools/AgentTool/prompt.ts:115-154，共 40 行，略）

原文依据：tools/AgentTool/prompt.ts:115-154。

主系统对 fork 自身还有“不再转派”的规则，见第 4 章（constants/prompts.ts:316-320）。两处配对后能看清委派责任：调用者决定范围并准备材料，执行者完成已界定任务，回报时给结果。提示里的性能或质量说法按文本保存，本章不把后台形式本身当成已经更快的证明。

选择前后台也不是“长任务一律后台”。描述按调用者是否马上需要结果决定，等待目标在通知到达后继续。若主任务没有结果便不能前进，仍把它放后台并不停查询输出，会偏离这里写的流程；若结果可稍后接入，就不必让主线程保存所有原始中间材料。

技能调用要么已加载，要么先加载

Skill 的描述要求匹配时先调用再对任务作其他响应，不能只说技能有用却不执行。已运行技能不能重复调用；看到 command-name 标签说明已加载，应遵循展开指令。可用技能列表来自 system-reminder，内建 CLI 命令排除在技能调用之外（C-17）。

原文依据：tools/SkillTool/prompt.ts:173-196。

Skill的阻塞条件发生在普通回复之前，因此它不是一般“可选的参考资料”。command-name标签又是宿主告诉模型已加载的状态信号；仅有system-reminder里的一行技能名还不等于完整prompt已经展开，调用时机正是这段协议要固定的地方。

这是一套加载状态的约定。名字列出、调用已发出、完整提示已展开，分别对应不同阶段；描述特意处理“已经出现指令”时该怎么办。它没有让模型把任意斜杠字符串猜成技能，名称集合的限制见第 4 章。清单预算又由第 14 章解释，调用协议与发现长度各有位置。

计划工具对歧义的门槛不同

计划门槛不是一份全局规范：相同的多文件请求在外部与内部文字中有不同位置。必须保留选择分支，才能解释“先规划”与“直接开始”为什么都出现在源码里（C-20）。

原文依据：tools/EnterPlanModeTool/prompt.ts:4-64。

外部与内部文案的差别不只是触发数量：外部强调“多文件”，内部要求真实歧义。相同用户请求在不同USER_TYPE分支可能得到不同的计划门槛；把外部清单抽成全局规则会抹掉这个条件。interview phase又说明流程文字可能转移到附件。

外部段的“何时使用”与“何时不使用”构成一对边界：多文件只是候选条件，纯研究又被排除。模型不能从一个命中项跳过其余排除项。

原文依据：tools/EnterPlanModeTool/prompt.ts:93-136。

内部段减少了明确任务的计划负担，但保留高影响重构和真实歧义的审批。两个版本都把用户批准留到计划完成后，差别在进入门槛，不在审批是否存在。

原文依据：tools/EnterPlanModeTool/prompt.ts:160-170。

如果只摘“多文件要计划”，就选中了外部版本中的一条，漏掉内部版本反过来限定的条件。完整源码也有 interview phase 省略共同流程段，因为详细步骤由附件提供。这里应从实际分支解释行为，而不是拼出一份不存在的“统一计划最佳实践”。

AskUserQuestion 用于澄清偏好、歧义和方案选择；它明确不能拿来问计划是否批准，因为用户在 ExitPlanMode 前看不到计划。ExitPlanMode 要求计划先写到指定文件，不从参数传正文，调用才把文件展示并请求批准；纯研究任务不适用。审批的对象和展示时机都由这个协议限定（C-21）。

原文依据：tools/AskUserQuestionTool/prompt.ts:32-44。

计划审批以文件为载体，AskUserQuestion以选项为载体。前者要求先写完整计划，后者禁止在用户看不到计划时问“是否同意”；如果把两者合成一项询问，模型会在没有可审查材料时提前请求授权。

澄清问题可以改变计划内容，ExitPlanMode只报告计划已写好。两个工具的输入对象因此不同，先后顺序不是UI偏好，而是确保审批对象已经存在。

原文依据：tools/ExitPlanModeTool/prompt.ts:6-29。

“问一个问题”和“请批准已经写好的计划”使用不同工具，不是表面交互样式的差别。若计划尚未展示就问用户“是否同意”，回答没有对应的可审查内容。工具描述给出了这一具体理由，可以用来解释调用顺序，不能仅按“都需要用户输入”归为同一步。

共享任务表保存依赖与所有者

创建任务不等于分派任务：默认状态和owner留空让这两步分开，描述还需支持另一个执行者接手。完成标准见第5章，这里检验共享记录能否表达尚未认领的工作（C-24）。

原文依据：tools/TaskCreateTool/prompt.ts:5-56。

pending是创建时状态，owner却要另一步设置；描述足够详细只是让被指派者能接手，不能替TaskUpdate完成认领。字段的默认值和协作语义因此分开：工具可以成功创建一项空owner任务，流程仍未完成派发。

TaskGet 要求开工前 blockedBy 为空，返回完整需求和依赖；TaskList 列摘要，把未认领、pending、无阻塞列为可做，建议按 ID 顺序，完成后查新解锁任务。TaskUpdate 更新前还要求先读取当前状态。状态、依赖和认领三者共同决定下一项，不是看到一个 pending 就直接开始（C-26、C-25）。

原文依据：tools/TaskGetTool/prompt.ts:1-24。

blockedBy为空是开始条件，TaskList的pending是候选状态，二者不是同一个判断。一个任务可能pending但有依赖，或未认领而可做；先取详情、再认领、完成后再查解锁项，正是提示词把状态查询接成流程的地方。

TaskGet提供双向依赖的完整需求，TaskList提供可扫的摘要；前者适合确认一项是否安全开工，后者适合寻找下一项。不能用摘要缺失的blockedBy字段替完整任务详情。

原文依据：tools/TaskListTool/prompt.ts:15-49。

TeamCreate 按建团队、建任务、派 agent、设 owner、执行、关闭排列步骤；成员名字用于通信，任务表用于协调。它说明消息自动投递，不需要人为轮询邮箱，也让执行者完成后看新解锁工作。当前章节可以据此还原协议，但不拿提示里的主动建团队偏好替用户授予无条件并行权限（C-27）。

原文依据：tools/TeamCreateTool/prompt.ts:1-63。

TeamCreate的顺序把团队目录、任务表、owner和通信地址连起来，但没有把所有任务都变成并行任务。创建团队是容器动作，具体是否值得协作仍由任务依赖和agent能力决定；提示词中的“鼓励”不能替代这两个条件。

队友能力先于owner分配，任务细节先于自动投递；这两个先后把“建立团队”与“开始实施”拆开。任务表随后才成为共享的协调面。

原文依据：tools/TeamCreateTool/prompt.ts:74-113。

成员名和任务owner把共享记录接到通信地址，自动投递又让队友无需轮询才能得到消息。它仍要求执行者看任务表找解锁工作，说明消息通知没有替代依赖状态；下一节正把这两条通道分开读。

消息与状态不能互相替代

通信与共享状态各有消费者，不能靠一条普通回复同时完成二者。SendMessage的协议明确接收地址和请求关联，而任务状态另交TaskUpdate；地址扩展又受UDS特性限制（C-28）。

原文依据：tools/SendMessageTool/prompt.ts:1-49。

消息与任务状态各有不可替代的信息：消息面向某个接收者，TaskUpdate面向共享表。广播“everyone”还会把成本线性扩散到成员数；所以团队协议要求只在全员确实需要时广播，而非把状态同步当消息广播。

这套要求区分了通知对方与更新共享记录。发一条“我做完了”不自动更新 owner 或 dependencies，写一个 completed 也不等于给特定队友答复问题。描述分别指定工具与字段，调用者要按对象选择。广播的线性成本是原文提示的理由，不能由它推出当前团队规模下的实际时延。

TaskStop 按 task_id 停后台任务；TeamDelete 删除团队和任务目录、清会话团队上下文，描述要求先关闭活跃成员。两种清理不是同一个动作，完成一个后台子任务并不自动结束整个团队（C-29）。

原文依据：tools/TaskStopTool/prompt.ts:1-8。

TeamDelete的失败条件在活跃成员，TaskStop只按task_id结束后台任务。一个任务停了，团队可能仍有成员和目录；一个团队关闭，也不等于逐项任务都得到成功状态。清理动作的对象范围需要从工具名和参数一起读。

TaskStop的失败只关联一个后台任务，TeamDelete的失败可能来自成员生命周期；因此清理顺序是状态依赖，不是两个独立按钮的排列。

原文依据：tools/TeamDeleteTool/prompt.ts:1-16。

团队删除还会清会话团队上下文，说明它影响的不只是磁盘目录。成员先关闭，是让这个上下文变化不会截断仍在运行的交接。

长驻流程还要约束等待与投递

Cron 描述按 durableEnabled 增减持久化文字，durable:true 要用户明确想保留任务；近似时间避开整点半点，明确时间则尊重指定值。运行说明还写 idle 时触发、jitter、到期和用户告知。它组织的是定时工作及其生命周期，不能把当前会话的提醒自动外推成长期调度（C-35）。

原文依据：tools/ScheduleCronTool/prompt.ts:68-135。

durable字段改变的是跨会话生命周期，时间近似规则改变的是调度分钟，idle触发说明改变的是运行上下文。三者并列在一个prompt里，却不会因为用户说“提醒我”就自动选择持久化。是否保存和何时触发是两种不同的授权问题。

Sleep 文案要求没事就等待，并提醒每次唤醒的 API 调用和缓存过期；Brief 把用户主要能见的回复放进 SendUserMessage，普通文字只在详细视图可见。这两份提示都让“发出了文本”不等于“用户看见最终结果”，结果该从哪个通道交付有明确要求（tools/BriefTool/prompt.ts:1-22、tools/SleepTool/prompt.ts:1-17）。

worktree 的进入、退出与丢弃授权已在第 4 章完整解释（tools/EnterWorktreeTool/prompt.ts:1-30、tools/ExitWorktreeTool/prompt.ts:1-32），本章不再重复。协作流程最终仍须回到实际执行：计划已批准，任务已认领，消息已交接，这些都不直接决定某次工具输入的 allow、deny、ask。下一卷从第 10 章追踪那个判定。
