E · 上下文与记忆预算第 14 章

窗口、字符与 token：几种预算各算什么

上下文卷按客户端计算、请求配置与文字要求分别取证，方法边界见阅读说明。本章从 utils/context.ts:8-16、utils/context.ts:27-112、utils/tokens.ts:40-65、utils/tokens.ts:214-261、services/tokenEstimation.ts:203-208 和 query.ts:280-280、query/tokenBudget.ts:3-19、query/tokenBudget.ts:45-93、utils/tokenBudget.ts:66-73、query.ts:1308-1339 检查预算。真正的问题是哪个消费者拿数量作什么决定：窗口控制材料容量，继续目标控制再做一轮，字符预算控制局部列表。数字相同，不能因此共用一个余额。

默认容量与本次采用的窗口不同

窗口常量只是能力选择的回退值；compact 输出常量也不是所有请求的同一输出额度。先保留这组不同用途的常量，再看覆盖的优先级（E-01）。

注释称当时所有模型二十万，后面的函数却已有多个更大窗口路径。常量说明与具体选择必须连读，不能单摘注释给整个程序固定容量。

原文依据：utils/context.ts:27-112。

内部正数覆盖优先于显式 [1m]，可以在仍使用大窗口端点时限制本地判断。禁用1M也不等于忽略所有模型能力字段，而是限制超默认窗口的相应分支。支持多少、本次按多少作阈值判断和客户端选择哪项，是三个需分别回答的问题。

已计入 usage 的历史与未发送尾部要对齐

窗口占用不能只加当前消息长度，也不能只看末次 API usage。后者描述过去一次请求，工具结果在响应后产生，下一次请求又会把它们带上（E-02）。

原文依据：utils/tokens.ts:40-65。

cache read 在计费上可能不同，但内容仍占当前窗口，所以这个消费者把缓存字段一起计入。output 也进入下次对话历史。这个口径首先用于容量判断，不能直接拿来当本轮生成目标或费用。

原文依据：utils/tokens.ts:214-261。

并行工具结果插在共享 message.id 的多个 assistant 分片之间，锚定最后一个分片会漏算更早结果。回到首个分片后再估尾部，把“服务器已计的前缀”和“尚未发送的材料”接到同一时点。这是消息结构导致的校正，不是换一个更精确的分词器。

长度除四是粗估，末次 usage 则来自响应；同一个总数里混合两种精度，仍有明确的适用范围。后面字符额度和显示宽度也各有计算，不宜因这里用四字符约一token，就把所有文字上限换算成严格token帽。

摘要输出空间和触发缓冲两次扣除

有效窗口要先给摘要留输出位置。这个预留在窗口缩小前按模型输出能力取较小值，环境覆盖只压小容量，不给它扩容（E-05）。

注释的17387分位数解释作者为何选两万，不是每次摘要必用17387。实现又取模型max output的较小者，实际预留可以低于两万；用一个观察数字替代公式，会把模型能力这个条件抹掉。

触发函数在有效窗口上再留缓冲，所以“窗口减预留”还不是自动压缩阈值。两次扣除分别给输出和触发留下空间（E-06）。

百分比覆盖用 min，只能让触发更早，不能推迟到常规阈值之后。警告、错误与手动缓冲另外服务不同事件，数值相同也不意味事件合并；还要看占用检查如何使用它们。

按已有公式代入一次就能看出两层的差别：假设窗口取默认二十万、模型允许预留满两万且没有环境覆盖，有效窗口为十八万，自动阈值再减一万三千，得到十六万七千。不能只减摘要预留就说“十八万触发”，也不能将注释里的摘要输出分位数直接替换两万常量。

阻塞阈值不是自动阈值的别名。余量可按自动触发基准算，同时临界标志按各自缓冲比较，这让界面百分比与是否该手动处理可能给出不同信息。是否运行主动压缩又由策略层决定，见第15章（services/compact/autoCompact.ts:147-183、services/compact/autoCompact.ts:185-239）。

局部字符预算容许历史超额

工具结果的aggregate额度限制单条user消息，不限制所有轮次结果总和。把两份十五万结果放在不同消息，和放在同一批并行结果里，按注释会得到不同处理（E-04）。

原文依据：constants/toolLimits.ts:35-49。

二十万字符与窗口二十万token没有同一单位；它防的是多工具单项限额叠成一条巨消息。具体是否启用、是否允许替换已见历史，还由下一块状态选择决定。

原文依据：utils/toolResultStorage.ts:415-463。

这里验证覆盖为有限正数，但开关关时连replacement state都不创建。恢复会话又冻结已见候选，避免模型先见完整结果、后来同一历史被换成预览。稳定重放优先于把旧消息重新压到当前额度内，例外接着落在替换选择器中。

原文依据：utils/toolResultStorage.ts:669-692。

冻结内容单独超额时接受超额；新候选选取又先减整个原大小，暂不知道预览占多少。故选择目标不宜说成对任何输入都严格封顶。源码注释已说明用近似尺寸选择，这个局部算法同时保留历史一致性与估算误差。

原文依据：utils/toolResultStorage.ts:912-936。

只有新替换才触发可选转录回调，持久化范围由调用方传不传callback决定；临时fork可以使用替换而不写转录。处理材料、重放选择和保存记录各有条件，不是一个名为budget的值自动完成所有动作。

技能预算按发现优先级分配

技能目录的每项帽与总表预算有不同强度。前者对包括内置在内的描述先裁切，后者为内置项保留优先级；“永不截断内置”只能对第二次分配成立（E-43）。

环境覆盖这里只以Number结果是否为真判断，没有像工具结果预算那样检查finite且positive。因此“预算覆盖都受同样正数校验”不成立。默认按窗口估百分之一也只是发现文字的计算，不能用来限制Skill调用取得的正文。

全表按stringWidth算，单项描述却按字符串length截；再保留内置描述或非内置名称，会使总量无法在任何输入下严格满足。它安排的是发现顺序里的取舍，不是删除工具能力。完整加载协议见第7、9章（tools/SkillTool/prompt.ts:173-196、tools/ToolSearchTool/prompt.ts:53-117、services/api/claude.ts:1207-1209、services/api/claude.ts:1231-1246）。

工作最低要求与实际停止条件有张力

TOKEN_BUDGET要让任务继续，不是在余量低时压缩上下文。构建开关先决定tracker是否存在，随后才有主agent、目标和增长判断（E-41）。

工具的后台预算或API参数不能自动创建这个tracker；这是当前查询循环的一条特性路径。其状态首先记录继续次数与前次增长，为停止决定提供历史，而不是只保留一个剩余数。

原文依据：query/tokenBudget.ts:3-19。

九成阈值与低收益判断服务不同停止理由。前者接近目标时停止，后者允许尚未接近却连续增长很少时停；要判断一轮为何结束，得看两个条件与计数，不只看最终百分比。

原文依据：query/tokenBudget.ts:45-93。

提示词称hard minimum，执行却可在九成或低收益时停。这是行为文字与实际循环条件的差别，两方都要保留。它也只推动主agent，不能从目标存在推断每个子agent都被自动续跑。

原文依据：utils/tokenBudget.ts:66-73。

续跑消息把目标差距写给模型并要求不要总结；消息本身不执行新任务。还要看调用方是否把它接回历史并继续query，才能把“请继续”从文案接成宿主动作。

原文依据：query.ts:1308-1339。

isMeta消息由宿主追加，用户没有重新发送请求，原工作仍是继续对象。这条状态转换与模型自行选择工具分开：它能再开一轮，却不替模型找出有价值的下一步。输出词数要求也不是整轮额度，相关文字见第6章（constants/prompts.ts:527-537、constants/prompts.ts:538-551）。

API余额跨压缩保存另一种计数

API task_budget的remaining不能因本地compact腾出空间就回满。参数注释先把它与自动续跑区别，避免把两个控制面字段混用（E-42）。

这份额度按agentic turn跨迭代计算，窗口压缩只改下一请求的材料。要保存之前消耗的判断基准，必须在替换数组之前取旧窗口，而不是拿新摘要大小扣余额。

原文依据：query.ts:504-535。

扣的是压缩前最终响应窗口，下限归零；compact成功不抹掉这次扣减。这个时点与前面的工具结果尾部估算不同，还要检查finalContext函数为何不用同一usage总和。

原文依据：utils/tokens.ts:68-112。

有iterations就取末项，没有则顶层input+output，两条都不加cache；它与本章开头窗口占用的含缓存算法不同。注释还承认服务端缓存口径是开放问题，不能把客户端一致的实现说成双方已核对。下一章沿这些不同基准，继续检查删除和恢复究竟改变了哪份材料。
