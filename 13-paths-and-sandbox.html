D · 权限与安全边界第 13 章

路径保护与沙箱执行

allow 是判定结果，文件和进程怎样执行还有具体条件。utils/permissions/filesystem.ts:606-665 的路径检查和 utils/sandbox/sandbox-adapter.ts:172-220 的沙箱配置转换是本章入口。值得放在一起读，是因为敏感路径、会话级豁免、符号链接与 OS 沙箱各处理不同边界；把它们压成一个“安全模式”会遮住例外和委派层。

路径检查同时看原路径和解析结果

checkPathSafetyForAutoEdit 使用预计算路径或 getPathsForPermissionCheck，遍历原路径与符号链接解析结果。可疑 Windows 形态返回 safe:false、classifierApprovable:false；Claude 配置和危险文件返回同样不安全，但可以交分类器批准。这个差别是返回字段，不是消息里一个语气强弱变化（D-42）。

原文依据：utils/permissions/filesystem.ts:606-665。

auto 对该字段的处理详见第 11 章，bypass 则不能直接越过 safetyCheck。检查名带 AutoEdit，不说明它的影响只局限在 acceptEdits；调用方怎样把 reason 返回到主管线才决定模式处理。路径检查与外层权限判定是一条真实调用链，需要两头对拍。

危险路径函数的注释列出 .git、IDE 与 shell 配置的原因：数据外泄、代码执行、编辑器设置或启动脚本被修改；还处理 UNC。匹配按统一大小写比较，.claude/worktrees 被当结构路径跳过这一层目录，但更深的危险目录仍检查。这是按路径片段作的豁免，不是整个 worktree 目录都失去保护（D-43）。

原文依据：utils/permissions/filesystem.ts:424-471。

这些原因来自注释，具体行为由循环和条件确认。用混合大小写命名或把敏感文件藏到符号链接后面，都是代码检查明确考虑的形态；但当前函数仍只证明检查点存在。团队记忆的深层真实路径检查稍后还会给出另一种实现，不能把所有路径验证都说成同一个标准化函数。

配置写入有窄会话豁免

写权限先查 deny，接着处理内部可编辑路径，再只搜索 session 的 .claude allow。规则必须处在项目或全局 .claude 范围，不能含 ..，以 /** 结束；收窄到单个 skill 的范围也可接受。随后才跑一般安全检查，建议也可以只授权这个 skill（D-44）。

原文依据：utils/permissions/filesystem.ts:1241-1338。

这条顺序是旧概括“敏感路径一律强制询问”需要校注的原因。工具自查内部已处理特定豁免，主判定拿到的可能是 allow；外层不能为一个已经没有 safetyCheck 的结果再执行那条检查。会话来源限定又防止宽泛永久授权意外替模型开放整片配置目录。

Shell 语法不只是一个命令前缀

Bash 安全模式表列出进程替换、命令和参数替换、zsh 扩展。注释举 =curl 为例：shell 会展开成可执行路径，解析器却看见 =curl，可能绕开 curl 前缀 deny。复合命令的逐子检查详见第 10 章，这里看另一个风险：同一执行行为可能由不同表面语法产生（D-56）。

原文依据：tools/BashTool/bashSecurity.ts:12-41。

前缀规则可以匹配已知字符串，不能自行理解所有 shell 展开。静态安全表为这些形态增加检查，内容级 deny 仍需适当的解析输入；这也是为何书中保留命令分析模块的接口，却不据有限模式表宣称 Bash 解析完整。遇到不支持或可疑语法，必须按返回行为查后续，不靠工具名概括结果。

权限规则转换成沙箱配置

网络 allowedDomains 来自 sandbox 设置与 WebFetch(domain:...) allow；开启只允许托管域名的策略时只取 policySettings。deny 域名另行收集。模型用 Bash 访问网络，沙箱仍可沿这些配置约束域名，因此工具权限来源与进程网络规则在转换器里接起来（D-45）。

原文依据：utils/sandbox/sandbox-adapter.ts:172-220。

初始 allowWrite 包含当前目录和 Claude 临时目录，denyWrite 无条件加入设置文件与托管 drop-in，还保护原目录与当前目录的 skills。注释直接把拒写 settings 和防沙箱逃逸关联，把 skills 与 commands/agents 的权限等级关联。这里说的是配置生成的拒写项，不是用户确认弹窗里的建议（D-46）。

原文依据：utils/sandbox/sandbox-adapter.ts:222-255。

Edit allow/deny 与 Read deny 分别转为 allowWrite、denyWrite、denyRead。sandbox.filesystem 的路径又按标准绝对路径解析，权限规则却可能使用设置相对语义；注释明确警告两者不同。把同样的 / 开头字符串从一个设置项复制到另一个，不能保证生成相同规则（D-47）。

原文依据：utils/sandbox/sandbox-adapter.ts:305-343。

配置转换不是重跑一遍提示词。它读设置、解析规则、填 runtime 字段；描述文本里的“默认在沙箱运行”只是对这个环境的告知。模型收到的目录限制和 OS 执行得到的配置有共同来源，但不能因显示文案删重或归一后，就认为实际允许路径也被同样改写。

不走沙箱还需读实际条件

excludedCommands 顶部注释明确说这是用户便利功能，不是安全边界，真正控制是会询问的沙箱权限系统。shouldUseSandbox 还查沙箱启用、显式禁用是否被策略允许以及命令是否存在；自动许可与允许无沙箱命令的设置未配时默认 true，不代表沙箱本身默认已开启（D-48）。

原文依据：utils/sandbox/sandbox-adapter.ts:468-477。

第 4 章已完整引用 shouldUseSandbox 与模型的逃逸重试文本，这里不再抄那段。Bash 权限自查在沙箱和自动许可开启、命令确实会沙箱化时调用 checkSandboxAutoAllow；注释强调尊重显式 deny/ask。沙箱自动许可是一条带条件的权限路径，不是一项覆盖全部用户规则的总开关（D-50）。

原文依据：tools/BashTool/bashPermissions.ts:1829-1844。

实际 Shell 在 shouldUseSandbox 为真时调用 SandboxManager.wrapWithSandbox；适配器等待初始化，否则报错，再交 BaseSandboxManager。调研到这里止于外部 runtime 委派，不能描述其内核策略已由本树独立核验。这个边界需要在本章明确，因为“已配置沙箱”与“我们审过其实现”不同（D-49）。

原文依据：utils/sandbox/sandbox-adapter.ts:704-725。

共享记忆还有写入与上传检查

团队路径验证先规范 .. 并检查字符串范围，再解析最深已有祖先的符号链接，确认实际目标仍在真实 team 目录。秘密 guard 在 TEAMMEM 下检查拟写内容，上传枚举又扫描并跳过命中文件。完整证据在 memdir/teamMemPaths.ts:222-256、services/teamMemorySync/teamMemSecretGuard.ts:3-44、services/teamMemorySync/index.ts:562-617，持久化用途与同步流程由第 16 章详述。这里保留另一处敏感写入跨过本地与共享边界的例子。

危险动作的可逆性、影响范围与用户授权文字，以及外来结果提示注入提醒，已由第 4 章配对说明（constants/prompts.ts:255-267、constants/prompts.ts:127-129、constants/prompts.ts:186-197、constants/cyberRiskInstruction.ts:24-24）。文字要求模型判断授权来源，实际代码检查具体参数、路径和运行环境。二者接在一起才构成当前控制面；其中任何一层都不能替其他层提供未审过的保证。

权限卷到此从一次输入走到执行环境。下一卷换一个限制对象：已经进入对话的消息、工具结果和记忆会占空间。第 14 章先分清窗口、字符估算和工作目标，随后再解释哪些内容会被回收。
